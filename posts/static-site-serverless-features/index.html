정적 사이트에 꼭 필요한 서버 기능만 붙이기

정적 홈페이지에서 비밀값이 필요하거나 입력을 다시 확인해야 하는 CMS 로그인, 문의 폼, 지원서 제출만 Vercel 함수로 처리했다. Word 지원서는 브라우저에서, 채용 공고 카드는 빌드 시점에 만들고, OAuth state 쿠키, Turnstile 재검증, 내용 해시로 막을 곳을 막았다.

지난 글에서 회사 홈페이지를 Astro 정적 사이트로 다시 만든 과정을 적었다. 설계 문서의 원칙은 “런타임 의존성 0”이었다. 서버를 없애려고 정적 사이트로 바꿨으니 서버 코드를 다시 들이고 싶지 않았다.

그래도 서버 없이는 안 되는 기능이 있었다. 비밀값을 써야 하거나, 방문자가 보낸 값을 믿을 수 없어 서버에서 다시 확인해야 하는 경우다. 그런 기능만 Vercel 함수로 붙이고 나머지는 빌드 시점이나 브라우저에서 처리했다. 이번에도 코드는 대부분 AI 코딩 에이전트가 썼다. 나는 무엇을 서버에 둘지 정하고 결과를 확인했다.

기능처리 위치서버가 필요한 이유
CMS 로그인Vercel 함수 2개OAuth client secret
문의 폼Vercel 함수메일 계정 비밀번호, 봇 확인 재검증
지원서 Word 파일브라우저필요 없음
채용 공고 카드빌드 시점필요 없음
지원서 온라인 제출Vercel 함수ERP 연동 키, 봇 확인 재검증

함수는 저장소의 api/ 폴더에 두고, 함수들이 같이 쓰는 코드는 api/_lib/에 넣었다. 밑줄로 시작하는 폴더는 Vercel이 주소로 만들지 않아서 공통 코드가 엔드포인트로 노출되지 않는다.

#Git 기반 CMS의 GitHub 로그인

기존 사이트에는 관리자 서버가 따로 있었다. 새 사이트에서는 Git 기반 CMS인 Sveltia CMS를 /admin에 붙였다. 콘텐츠가 저장소의 YAML과 Markdown 파일이므로 CMS는 그 파일을 고치는 편집 화면 역할만 한다. 저장하면 바로 운영에 올라가지 않고 PR이 만들어진다. Vercel 미리보기로 확인하고 “게시”를 누르면 main에 병합된다.

CMS는 브라우저에서 GitHub API를 직접 부르는데, 로그인이 문제였다. GitHub OAuth에서 code를 토큰으로 바꾸려면 client secret이 필요하고, 이 값은 브라우저에 둘 수 없다. 그래서 로그인 시작(/api/auth)과 콜백(/api/callback) 함수 두 개를 만들었다.

#state 쿠키로 요청 위조 막기

시작 함수는 임의의 state를 만들어 GitHub 인증 주소에 붙이고 같은 값을 쿠키에도 넣는다. 콜백은 GitHub가 돌려준 state와 쿠키 값이 같은지 본다. 다르면 다른 곳에서 시작된 로그인으로 보고 거절한다.

쿠키 경로를 /api로 좁혀서 사이트의 다른 페이지 요청에는 실리지 않게 했다. 콜백은 처리가 끝나면 이 쿠키를 Max-Age=0으로 지운다.

#postMessage로 결과 넘기기

CMS는 로그인을 팝업 창으로 연다. 콜백이 토큰을 받으면 그 결과를 원래 CMS 창에 넘겨야 한다. Decap·Sveltia 계열 CMS에는 정해진 postMessage 규약이 있다. 팝업이 먼저 authorizing:github를 보내고, CMS 창이 같은 문자열로 답하면 그때 authorization:github:success:{...} 형태로 토큰을 보낸다.

여기서 지킨 원칙은 하나다. 토큰은 이 사이트와 같은 출처의 창에만 보낸다. 대상 출처를 *로 두면 다른 사이트가 로그인 창을 열었을 때 토큰이 그 사이트로 넘어갈 수 있다.

메시지를 스크립트 안에 넣을 때 <를 \u003c로 바꿨다. 에러 메시지에 </script> 같은 문자열이 섞여도 스크립트 태그가 중간에 닫히지 않게 하려고 넣은 처리다. 응답에는 Cache-Control: no-store를 붙였다.

#문의 폼과 봇 확인 재검증

사업 문의 폼은 입력값을 메일로 보낸다. 메일 계정 비밀번호가 필요하니 서버에서 처리해야 한다. 폼을 공개하면 스팸이 온다는 것도 전제로 두고, 막는 장치를 여러 겹 두었다.

  1. Origin 헤더가 이 사이트가 아니면 거절한다.
  2. 같은 IP에서 10분에 5번까지만 받는다. 함수 인스턴스 메모리 안에서만 세는 간단한 제한이다.
  3. 사람 눈에 안 보이는 칸이 채워졌거나 폼을 연 지 3초 안에 보냈으면 봇으로 보고, 봇에게는 성공한 것처럼 응답한다.
  4. Cloudflare Turnstile 토큰을 서버에서 다시 확인한다.

이 중 4번이 중요하다. 브라우저에서 Turnstile 위젯을 통과해야 버튼이 눌리게 해도, 함수 주소로 직접 요청을 보내면 위젯을 건너뛸 수 있다. 그래서 서버가 토큰을 받아 siteverify에 다시 물어본다.

주의

확인 서버에 닿지 못할 때 통과시키는 것은 일부러 정한 동작이다. 문의 폼에서는 스팸 몇 건보다 진짜 문의를 놓치는 쪽이 손해가 더 크다고 봤다. 이때도 Origin, 횟수 제한, 숨은 칸은 그대로 동작한다. 로그인처럼 막는 쪽이 중요한 곳에서는 반대로 해야 한다.

fetchFn을 인자로 받게 한 것은 테스트 때문이다. 가짜 fetch를 넣어 토큰 없음, 실패, 성공, 500 응답, 연결 실패의 다섯 경우를 확인했다. Turnstile은 키를 넣었을 때만 켜진다. 메일 설정이 없으면 함수가 503과 “준비 중”을 돌려주고, 화면은 폼을 잠그고 이메일 문의를 안내한다.

#원본 Word 양식을 브라우저에서 채우기

채용 지원자는 회사의 입사지원서 Word 양식을 받아 채워서 보내 왔다. 이 양식을 웹에서 입력하고 Word 파일로 받을 수 있게 했는데, 서버는 쓰지 않는다. 지원자의 개인정보가 서버를 거칠 필요가 없고, 작성 중인 내용은 그 브라우저에만 임시 저장된다.

원본 .docx를 받아 압축을 풀고(fflate), word/document.xml의 표 셀 위치에 값을 넣은 뒤 다시 압축한다. 새 문서를 만들지 않고 원본을 채우기 때문에 글꼴, 칸 너비, 테두리가 양식 그대로 남는다.

셀은 좌표로 찾는다. “표1의 0행 1열은 성명”처럼 양식 구조를 주석에 적어 두고, 양식 파일이 바뀌면 좌표도 같이 고친다. 처리를 몇 가지 더 넣었다.

  • 값을 넣을 때 셀 문단의 기본 글꼴은 이어받고, 안내 문구의 파란 글자색은 검정으로 바꾼다.
  • 자격증이 칸보다 많으면 행을 복제해 늘린다. 기술경력 표는 빈 행을 하나 떼어 두고 프로젝트 수만큼 복제한다.
  • 기술경력 기간 합계를 계산해 제목 옆에 붉은 글씨로 붙인다. 프로젝트 기간이 겹치는 달은 한 번만 센다.

#DOM 구현을 주입받아 테스트하기

XML을 다루려면 DOMParser와 XMLSerializer가 필요한데, 브라우저에는 있고 Node에는 없다. 그래서 채우는 함수가 DOM 구현을 인자로 받게 했다.

테스트는 실제 양식 파일을 채운 뒤 결과 XML을 다시 읽어 셀 내용을 확인한다. 회사가 작성하는 칸이 양식 그대로인지, 입력하지 않은 학력 행은 건드리지 않았는지, 프로젝트가 43개면 행도 정확히 43개인지 같은 것들이다. 양식이 바뀌어 좌표가 어긋나면 npm test에서 바로 드러난다. 테스트 파일은 .ts 그대로 Node로 실행한다.

#채용 공고 카드는 빌드할 때 만든다

채용 공고는 외부 채용 사이트에 올린다. 홈페이지에서는 데이터 파일에 공고 주소만 넣으면 제목, 조건, 마감일이 들어간 카드가 나오게 했다.

공고 내용을 런타임에 서버에서 가져올 필요는 없었다. 빌드할 때 공고 페이지를 받아 og:title과 og:description만 읽는다. 링크를 공유할 때 미리보기로 보이는 공개 정보다. 설명 문자열을 “항목 : 값” 단위로 쪼개 조건 목록과 마감일로 나눈다. 파서는 순수 함수로 분리해 테스트했다.

외부 사이트가 잠깐 응답하지 않는다고 회사 홈페이지 배포가 막히면 안 된다. 그래서 조회에 실패하면 경고만 남기고 링크 카드로 바꾼다. 제목과 마감일은 데이터 파일에서 직접 덮어쓸 수도 있다.

빌드 시점에 받은 데이터는 시간이 지나면 낡는다. 그래서 GitHub Actions로 매일 새벽 3시(KST)에 Vercel 배포 훅을 호출해 다시 빌드한다. 이때 공고 정보와 함께 업력 연도도 갱신된다. 마감일이 지난 공고는 다음 빌드를 기다리지 않고 방문자 브라우저에서 바로 숨긴다.

#내용 해시로 중복 접수 막기

나중에 지원서를 회사 ERP로 바로 보내는 기능이 붙었다. 이 함수에서 가장 신경 쓴 것은 중복 접수다. 제출 버튼을 두 번 누르거나, 응답이 늦어 다시 보내거나, 일부러 같은 요청을 반복해도 ERP에는 한 건만 들어가야 한다.

그래서 지원서 번호를 서버가 내용으로 만들게 했다. 입력값을 정리(앞뒤 공백 제거, 빈 항목 제거)한 뒤 SHA-256 해시를 내고 그 앞부분을 번호로 쓴다. ERP는 같은 번호가 이미 있으면 새로 넣지 않고 “이미 접수됨”으로 답한다.

해시에 무엇을 넣을지가 중요했다. 동의 시각을 넣으면 보낼 때마다 번호가 달라져 중복을 잡지 못한다. 그래서 동의 정보와 첨부 파일은 해시를 만든 뒤에 붙였다. 테스트로 이름 앞뒤에 공백이 있거나 빈 자격증 칸이 있어도 같은 번호가 나오는지, 전화번호가 다르면 다른 번호가 나오는지 확인했다.

참고

같은 내용이 다시 오는 것과 같은 사람이 다시 지원하는 것은 서로 다른 문제다. 앞의 것은 홈페이지가 번호로 막고, 뒤의 것(재지원 기간)은 ERP가 판단한다. 브라우저도 마지막 제출 정보를 기억해 두어, 같은 사람이 기간 안에 다시 누르면 요청을 보내지 않고 안내만 띄운다.

ERP 주소나 키가 설정되지 않으면 함수는 꺼져 있다고 알리고, 화면은 “온라인으로 제출” 버튼을 숨긴 채 예전처럼 Word 파일 만들기만 보여 준다. 기능 하나가 준비되지 않았다고 페이지 전체가 깨지지 않게 한 방식은 문의 폼과 같다.

#정리

  • 서버는 비밀값이 필요하거나 입력을 다시 확인해야 하는 기능, 즉 CMS 로그인, 문의 폼, 지원서 온라인 제출에만 붙였다.
  • CMS OAuth는 함수 두 개로 처리했다. state 쿠키로 같은 브라우저인지 확인하고, 토큰은 같은 출처 창에만 postMessage로 넘긴다.
  • 봇 확인은 브라우저 위젯만으로는 부족해서 서버에서 siteverify로 다시 확인했다. 확인 서버 장애 때 통과시킬지는 기능마다 따로 정한다.
  • Word 지원서는 원본 양식의 표 셀을 채워 브라우저에서 만든다. DOM 구현을 주입받게 해서 Node에서 xmldom으로 같은 코드를 테스트했다.
  • 채용 공고 카드는 빌드 때 og 메타로 만들고, 조회에 실패해도 빌드는 계속한다. 매일 다시 빌드해 낡은 정보를 갱신한다.
  • 지원서 번호를 내용 해시로 만들어 같은 요청이 여러 번 와도 한 번만 접수되게 했다.
  • 설정이 빠진 기능은 꺼진 상태로 동작하게 해서, 준비가 덜 된 기능 때문에 사이트가 깨지지 않게 했다.
