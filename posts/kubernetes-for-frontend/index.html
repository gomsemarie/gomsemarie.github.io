프론트엔드 개발자가 쿠버네티스를 이해해야 하는 이유

솔직히 말하면 처음에는 “이거 백엔드 일 아니야?”라고 생각했다. 근데 팀에서 프론트엔드 앱 배포까지 직접 하게 됐고, Kubernetes를 피할 수 없게 됐다. 처음엔 낯설었지만, 개념을 잡고 나니 오히려 배포에 대한 불안감이 많이 줄었다.

#쿠버네티스가 뭐냐고?

컨테이너(Docker)를 여러 서버에 걸쳐 자동으로 관리해주는 오케스트레이션 시스템이다. 쉽게 말하면 “이 앱을 항상 3개 인스턴스 켜놔, 하나 죽으면 새로 시작해, 트래픽 많으면 자동으로 늘려”라는 명령을 선언적으로 설정해두면 알아서 해준다.

#프론트엔드 앱의 컨테이너화

React나 Gatsby 같은 정적 사이트는 빌드하면 HTML/CSS/JS 파일 묶음이 나온다. 이걸 nginx로 서빙하는 컨테이너를 만드는 게 기본이다.

nginx 설정도 중요하다. SPA의 경우 클라이언트 라우팅 때문에 모든 경로를 index.html로 떨궈야 한다.

#핵심 Kubernetes 개념 — 프론트엔드 관점에서

#Pod

가장 작은 배포 단위. 내 nginx 컨테이너 하나가 Pod 하나라고 보면 된다.

#Deployment

Pod를 몇 개 유지할지, 어떻게 업데이트할지 정의한다. 이게 진짜 중요하다.

RollingUpdate 전략이 핵심이다. 배포할 때 이전 Pod를 모두 죽이고 새 걸 띄우는 게 아니라, 순차적으로 교체한다. 덕분에 다운타임 없이 배포된다.

#Service

Pod에 접근하기 위한 고정된 네트워크 엔드포인트. Pod는 죽었다 살아나면 IP가 바뀌는데, Service는 항상 같은 주소를 제공한다.

#Ingress

외부 트래픽을 클러스터 내부 Service로 라우팅한다. 도메인, HTTPS, 경로 기반 라우팅을 여기서 설정한다.

#ConfigMap & Secret

환경 변수 주입에 사용한다. Gatsby나 Next.js의 환경 변수 파일(.env)을 컨테이너에 넣는 방법이다.

단, Gatsby 같은 정적 사이트는 빌드 시점에 환경 변수가 번들에 포함된다. 런타임 주입이 의미 없다. 이 경우 이미지 빌드 시 --build-arg로 넘기거나, 런타임 환경 변수를 window.__ENV__ 형태로 HTML에 주입하는 패턴을 쓴다.

#HPA — 자동 스케일링

트래픽이 갑자기 몰릴 때 Pod를 자동으로 늘려준다.

정적 사이트는 nginx가 워낙 가볍기 때문에 CPU가 60% 가는 경우가 드물긴 하다. 그래도 설정해두면 안심된다.

#배포 파이프라인 흐름

kubectl rollout status로 배포 완료를 기다린다. 실패하면 CI가 에러를 잡아준다.

#롤백

배포 후 문제가 생기면 즉시 이전 버전으로 되돌릴 수 있다.

이게 진짜 마음의 안정을 준다. 배포 잘못해도 10초 만에 되돌릴 수 있다.

#내가 겪은 흔한 실수들

1. latest 태그 사용 image: frontend:latest는 절대 쓰지 마라. 어떤 버전인지 추적이 안 되고, 같은 태그여도 imagePullPolicy에 따라 다른 이미지를 쓸 수 있다. 항상 커밋 SHA나 버전 태그를 쓴다.

2. readinessProbe 없음 없으면 Pod가 완전히 준비되기 전에 트래픽이 들어와서 에러 응답이 나간다. nginx 기반이면 /에 200 응답 확인하는 readinessProbe는 기본으로 넣자.

3. 리소스 limits 미설정 프론트엔드 컨테이너는 가벼워서 그냥 두기 쉬운데, limits가 없으면 노드 리소스를 독차지할 수 있다. 작게라도 설정해두자.

4. ConfigMap 변경 후 Pod 재시작 안 함 ConfigMap을 바꿔도 이미 실행 중인 Pod에는 자동으로 반영되지 않는다. kubectl rollout restart deployment/frontend-app으로 재시작해야 한다.

K8s가 처음엔 진입 장벽이 높아 보이지만, 개념을 이해하면 오히려 배포가 더 안전하고 예측 가능해진다. 특히 롤링 업데이트와 롤백 기능은 한 번 써보면 이전으로 돌아가기 싫어진다.
