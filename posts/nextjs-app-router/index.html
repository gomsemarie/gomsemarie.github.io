Next.js App Router 완전 정복 — React 개발자를 위한 가이드

Next.js 13에서 App Router가 나왔을 때 솔직히 “또 배워야 해?”라는 생각이 먼저 들었다. Pages Router에 익숙해졌는데 갑자기 app/ 디렉토리에 layout.tsx, loading.tsx, error.tsx… 파일 컨벤션이 완전히 달라졌다. 하지만 14, 15 버전을 거치면서 안정화됐고, 이제는 새 프로젝트에 App Router를 안 쓸 이유가 없다.

#라우팅 구조 — 폴더가 곧 경로다

App Router에서는 app/ 아래 폴더 구조가 URL 경로가 된다.

특수 파일들이 각자 역할을 가진다.

파일역할
layout.tsx중첩 레이아웃, 리렌더 없이 유지됨
page.tsx해당 경로의 UI
loading.tsxSuspense 기반 로딩 UI
error.tsx에러 바운더리
not-found.tsx404 처리
template.tsxlayout과 달리 이동 시 새로 마운트됨

#Server Components vs Client Components

이게 App Router의 핵심이자 가장 헷갈리는 부분이다.

Server Components (기본값)

서버에서만 실행되기 때문에 번들에 포함되지 않는다. DB 접근, API 키 노출 없이 서버 작업이 가능하다.

Client Components

useState, useEffect, 이벤트 핸들러가 필요한 건 Client Component여야 한다.

중요한 규칙: Server Component에서 Client Component를 import할 수 있지만, 반대는 안 된다.

#데이터 패칭 — fetch가 달라졌다

App Router에서는 getStaticProps, getServerSideProps가 없다. 대신 컴포넌트 안에서 바로 fetch를 비동기로 호출한다.

#Streaming과 Suspense

App Router의 강력한 기능 중 하나다. 느린 데이터를 기다리는 동안 나머지를 먼저 보내준다.

loading.tsx는 라우트 전체에 자동 Suspense를 적용한다.

#Server Actions — 폼 제출이 이렇게 간단해도 되나

Server Actions는 서버에서 실행되는 함수를 클라이언트에서 직접 호출할 수 있게 해준다.

action={submitContact}만 넣으면 폼 제출 시 서버 함수가 실행된다. API 라우트 만들 필요가 없다. JavaScript가 꺼진 환경에서도 동작한다.

낙관적 업데이트도 쉽다.

#Metadata API

<head> 태그 관리가 명료해졌다.

#Parallel Routes와 Intercepting Routes

고급 패턴이지만 알아두면 좋다.

Instagram처럼 피드에서 사진 클릭하면 모달로 뜨고, URL 직접 입력하면 전체 페이지로 뜨는 패턴을 구현할 수 있다.

#Pages Router vs App Router 마이그레이션 전략

기존 Pages Router 프로젝트를 마이그레이션할 때는 점진적으로 해야 한다.

두 라우터가 공존할 수 있기 때문에 한 번에 다 바꾸지 않아도 된다.

App Router는 처음 진입 장벽이 있지만, 한 번 익숙해지면 Pages Router로 돌아가기 싫어진다. 특히 Server Components + Streaming 조합은 데이터가 많은 페이지에서 체감이 확실하다. 새 프로젝트를 시작한다면 App Router를 쓰자.
