AI 코딩 에이전트로 회사 ERP를 열흘 동안 옮겼다: 458커밋의 흐름

오래된 Java ERP를 Next.js와 PostgreSQL로 옮기면서 AI 코딩 에이전트에게 이식과 대조를 맡겨 열흘 동안 458커밋을 쌓았다. 첫날 데이터와 API 대부분이 옮겨진 조건과, 사람이 직접 결정한 자리를 적었다.

회사 ERP를 새 스택으로 옮기고 있다. 인력, 급여, 계약, 매출·매입을 관리하는 사내 시스템이다. 기존 시스템은 Spring Boot + MyBatis API와 별도 웹 화면으로 되어 있었고, 클라우드 VM과 관리형 DB, 오브젝트 스토리지 위에서 돌았다. 새 시스템은 Next.js 프로젝트 하나에 화면과 API를 같이 두고 DB는 관리형 PostgreSQL을 쓴다. 폐쇄망에도 그대로 설치할 수 있어야 한다는 조건도 있었다.

이 시리즈에는 이관하면서 겪은 일을 주제별로 나눠 적는다. 첫 글은 전체 흐름이다. 10월 7일부터 16일까지 열흘 동안 저장소에 쌓인 커밋은 458개다. 그중 445개는 내가 운영한 AI 코딩 에이전트가 작성했다. 나머지는 동료가 올린 근태·휴가 개편 9개와 자동화 봇 커밋 4개다.

#순서: 재현, 사용성, 새 기능

저장소 README 맨 위에 작업 순서를 적어 두었다.

  1. 기존 기능을 100% 똑같이 재현한다.
  2. 그다음 화면과 사용성을 고친다.
  3. 마지막에 새 기능을 더한다.

기존 ERP 코드는 전환 때까지 동결했다. 코드가 바뀌지 않으니 새 API가 맞는지 판단할 기준으로 쓸 수 있다. 재현을 맨 앞에 둔 이유는 급여나 정산 금액 때문이다. 기존과 1원이라도 다르면 그게 개선인지 버그인지 따지는 데만 며칠이 걸린다. 그래서 같다는 것을 먼저 확인하고, 바꿀 것은 하나씩 결정해서 바꾸기로 했다.

#첫날 데이터와 API를 옮긴 순서

첫날 커밋은 69개다. 시각 순으로 보면 이렇다.

시각한 일
13:33저장소 시작. 전환 계획 문서, 기존 API 전체 대조표, 이관 스크립트
13:43기존 DB 덤프 → 새 DB 복원. 테이블별 행 수, 내용 해시, 시퀀스, 함수, 트리거, 인덱스까지 원본과 대조

14:35주민번호 재암호화. 기존 AES/ECB를 복호화해 AES-256-GCM(키 버전 포함)으로 다시 저장
14:48로그인 계정 생성, 첨부 구조 개편

16:40쓰기 API 대조. 시나리오 80개 중 70개 일치, 나머지 10개는 의도한 차이

20:18전환 당일 리허설과 절차서

이식하지 않은 API 중 3개는 새 구조로 대체했고(파일 업로드, 상태 확인 등), 4개는 샘플·첫 화면용이라 뺐다. 메신저 발송 기능은 쓰는 사람이 없어서 결정을 받아 범위에서 뺐다.

재암호화를 먼저 하면서 생긴 문제도 있다. 새 DB의 주민번호는 새 형식이라 기존 Java API가 읽지 못한다. 그래서 대조에 쓰는 기존 API는 새 DB 대신 덤프를 복원한 로컬 DB에 붙여 띄웠다. 대조 환경은 다음 글에 따로 적었다.

10일과 11일은 주말이라 커밋이 없다. 이관의 뼈대는 첫날 끝났고, 둘째 날부터는 재현보다 사용성 쪽 일이 많았다. 커밋이 가장 많은 날은 9일인데, 대부분 화면을 고친 작은 커밋이다. 그리드에서 한글 첫 글자가 사라지는 문제 하나에도 커밋이 여러 개 들어갔다(이 문제는 따로 적었다).

13일에는 사내 요청 창구와 에이전트를 연결했다. 요청을 확정하면 CI에서 에이전트가 작업 브랜치를 만들고 미리보기 주소를 남긴다. 봇 커밋 4개는 이 경로로 들어왔다.

#사람이 맡은 일

커밋 작성자만 보면 사람이 한 일이 없어 보이지만, 몇 가지는 사람이 직접 맡았다.

동작을 바꾸는 결정. 기존 버그를 고치거나 동작을 바꿔야 하는 항목은 에이전트가 바로 고치지 않고 결정 목록에 올렸다. 사람이 승인한 뒤에 반영했다. 대조 문서에는 “사용자 결정 반영” 항목이 따로 있어서, 결정마다 대조 기준 수치가 어떻게 바뀌었는지 남아 있다.

원칙을 벗어난 개선 되돌리기. 첫날 18시 39분에 급여 계산을 서버 한 곳으로 모으는 커밋이 들어갔다. 코드는 더 깔끔해졌지만 기존 급여와 보고서 금액이 바뀌는 변경이었다. 2분 뒤 되돌렸고, 알려진 계산 차이는 현행 유지로 문서에 적었다. 재현을 먼저 하기로 한 이상, 이런 개선은 사람이 보고 막아야 했다.

단계별 병합. 작업 브랜치에서 개발 통합 브랜치로, 다시 운영 브랜치로 가는 병합은 사람이 확인하고 진행했다. 동료의 근태·휴가 개편도 단계마다 PR로 들어왔다. 14일에는 DB 마이그레이션이 든 PR을 개발 DB 적용이 확인되기 전에는 합치지 못하게 하는 검사를 넣었다.

운영 DB 마이그레이션. 운영 DB에 구조 변경을 적용하는 일은 사람이 직접 실행했다. 에이전트용 안내문에도 “운영 DB 마이그레이션은 사람이 직접 실행한다”를 규칙으로 넣었다. 전환 당일 절차서에는 단계마다 실행 주체를 적었고, 덤프·재암호화처럼 되돌리기 어려운 단계는 사람이 하거나 사람이 승인한 에이전트가 하도록 정했다.

참고

에이전트에게는 옮기고, 대조하고, 차이를 보고하는 일을 맡겼다. 그 차이를 받아들일지는 맡기지 않았다. 이 선을 미리 정해 두어서 빠르게 진행하면서도 크게 불안하지 않았다.

#첫날 빨리 진행된 이유

첫날 속도는 에이전트가 빨라서라기보다 조건이 맞아서 나왔다고 본다.

비교할 기존 시스템이 있었다. 기존 API를 동결해 로컬에 띄우고, 같은 요청을 두 API에 보내 응답과 DB 변화를 비교했다. 에이전트는 맞게 옮겼다는 말 대신 대조 결과를 내놓았고, 나는 수백 개 API를 다 읽지 않고 불일치 목록만 보면 됐다.

SQL을 옮기지 않았다. 기존 SQL 429개를 TypeScript로 하나씩 옮겼다면 하루에 끝낼 수 없었다. 매퍼 XML을 그대로 읽어 실행하는 작은 해석기를 먼저 만들었고, 그 뒤로 API 이식은 Java 서비스 코드를 한 줄씩 옮기는 일만 남았다. 해석기는 3편에 적었다.

계획을 문서로 먼저 고정했다. docs/PLAN.md 하나에 목표 구조, 결정 사항, 범위에서 뺀 기능, 이관 기록을 모았다. 에이전트는 작업을 시작할 때마다 이 문서를 읽고, 끝나면 기록을 고쳤다.

마지막 줄의 재실행 순서가 특히 중요했다. 첫날 한 이관은 1차이고, 전환 당일에는 같은 스크립트를 같은 순서로 다시 돌려 운영 데이터를 덮어쓴다. 그래서 이관 스크립트는 모두 여러 번 돌려도 안전하게 만들었고, 순서는 문서에 고정했다. 보안, 파일, 권한, 폐쇄망 같은 주제별 문서도 따로 두었다. 폐쇄망 문서에는 “새 라이브러리는 MIT·Apache-2.0·BSD 계열만” 같은 규칙을 적었고, 에이전트는 라이브러리를 고를 때 이 규칙을 따랐다.

#한계

비교할 기준이 없는 일은 느렸다. 화면은 기존과 똑같이 만드는 게 목표가 아니었다. 대조할 대상이 없으니 사람이 직접 눌러 보고 고쳐 달라고 해야 했다. 9일의 커밋 124개가 대부분 그렇게 나왔다. 한글 입력, 포커스 테두리, 정렬 버튼처럼 직접 써 봐야 아는 문제들이다.

자동 점검이 없는 곳은 늦게 알았다. 매일 도는 백업이 9일부터 실패하고 있었는데 14일에야 고쳤다. 환경변수가 빈 문자열이면 백업 도구가 그 값을 숫자로 읽지 못해 업로드 전에 멈췄다. 운영 로그인 오류도 사용자가 알려 줘서 알았다. 그래서 개선 검토 문서 첫 줄에 “주요 업무 흐름 자동 점검”과 “운영 오류 알림”을 올렸다.

병렬 작업은 충돌을 남겼다. 서로 다른 브랜치에서 같은 번호의 마이그레이션을 만들거나, 합치다가 같은 코드가 두 번 들어간 일이 있었다. 에이전트가 빨리 만들수록 브랜치 사이를 정리하는 일은 사람이 더 챙겨야 했다.

커밋 수로 결과를 판단할 수는 없다. 458개 중에는 한 줄짜리 수정도 많다. 커밋 수는 속도를 보여 줄 뿐이고, 맞게 옮겼다는 근거는 대조 결과에 있다.

주의

비교할 기존 시스템이 없는 새 기능에서 같은 속도를 기대하면 안 된다. 이관이 빨랐던 것은 “기존과 같은가”를 기계로 확인할 수 있었기 때문이다.

#정리

  • 순서를 재현, 사용성, 새 기능으로 정하고, 동결한 기존 코드를 비교 기준으로 썼다.
  • 첫날 DB·파일 이관, 재암호화, API 대부분 이식, 조회·쓰기 대조까지 끝났다. SQL을 옮기지 않고 그대로 실행한 영향이 컸다.
  • 에이전트에게는 옮기기, 대조, 보고를 맡겼다. 동작을 바꿀지, 병합할지, 운영 DB를 바꿀지는 사람이 정했다.
  • 계획과 결정, 재실행 순서를 한 문서에 모아 에이전트와 사람이 같은 기준을 봤다.
  • 비교할 기준이 없는 화면 작업과 자동 점검이 없는 운영 영역은 여전히 사람이 직접 봐야 했다.

다음 글에는 “기존과 같다”를 어떻게 확인했는지, 대조 테스트를 자세히 적는다.
