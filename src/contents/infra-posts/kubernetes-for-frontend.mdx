# 프론트엔드 개발자가 쿠버네티스를 이해해야 하는 이유

솔직히 말하면 처음에는 "이거 백엔드 일 아니야?"라고 생각했다. 근데 팀에서 프론트엔드 앱 배포까지 직접 하게 됐고, Kubernetes를 피할 수 없게 됐다. 처음엔 낯설었지만, 개념을 잡고 나니 오히려 배포에 대한 불안감이 많이 줄었다.

## 쿠버네티스가 뭐냐고?

컨테이너(Docker)를 여러 서버에 걸쳐 자동으로 관리해주는 오케스트레이션 시스템이다. 쉽게 말하면 "이 앱을 항상 3개 인스턴스 켜놔, 하나 죽으면 새로 시작해, 트래픽 많으면 자동으로 늘려"라는 명령을 선언적으로 설정해두면 알아서 해준다.

## 프론트엔드 앱의 컨테이너화

React나 Gatsby 같은 정적 사이트는 빌드하면 HTML/CSS/JS 파일 묶음이 나온다. 이걸 nginx로 서빙하는 컨테이너를 만드는 게 기본이다.

```dockerfile
# 멀티스테이지 빌드 — 빌드 결과물만 이미지에 담는다
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN npm install -g pnpm && pnpm install --frozen-lockfile
COPY . .
RUN pnpm build

FROM nginx:alpine AS runner
COPY --from=builder /app/public /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

nginx 설정도 중요하다. SPA의 경우 클라이언트 라우팅 때문에 모든 경로를 `index.html`로 떨궈야 한다.

```nginx
# nginx.conf
server {
  listen 80;
  root /usr/share/nginx/html;
  index index.html;

  # gzip 압축 — 번들 사이즈를 확 줄여준다
  gzip on;
  gzip_types text/plain text/css application/json application/javascript;
  gzip_min_length 1000;

  # 정적 자산은 캐싱
  location ~* \.(js|css|png|jpg|ico|svg|woff2)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
  }

  # SPA 라우팅
  location / {
    try_files $uri $uri/ /index.html;
  }
}
```

## 핵심 Kubernetes 개념 — 프론트엔드 관점에서

### Pod

가장 작은 배포 단위. 내 nginx 컨테이너 하나가 Pod 하나라고 보면 된다.

### Deployment

Pod를 몇 개 유지할지, 어떻게 업데이트할지 정의한다. 이게 진짜 중요하다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-app
  namespace: production
spec:
  replicas: 3            # 항상 3개 Pod 유지
  selector:
    matchLabels:
      app: frontend-app
  strategy:
    type: RollingUpdate  # 무중단 배포
    rollingUpdate:
      maxSurge: 1        # 업데이트 중 최대 1개 추가 생성
      maxUnavailable: 0  # 업데이트 중 비가용 Pod 없음
  template:
    metadata:
      labels:
        app: frontend-app
    spec:
      containers:
        - name: frontend
          image: my-registry/frontend:v1.2.3  # 항상 구체적인 태그 사용
          ports:
            - containerPort: 80
          resources:
            requests:
              memory: "64Mi"
              cpu: "50m"
            limits:
              memory: "128Mi"
              cpu: "200m"
          readinessProbe:       # 준비되기 전엔 트래픽 안 보냄
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10
```

`RollingUpdate` 전략이 핵심이다. 배포할 때 이전 Pod를 모두 죽이고 새 걸 띄우는 게 아니라, 순차적으로 교체한다. 덕분에 다운타임 없이 배포된다.

### Service

Pod에 접근하기 위한 고정된 네트워크 엔드포인트. Pod는 죽었다 살아나면 IP가 바뀌는데, Service는 항상 같은 주소를 제공한다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: frontend-service
spec:
  selector:
    app: frontend-app
  ports:
    - port: 80
      targetPort: 80
  type: ClusterIP  # 클러스터 내부용, 외부엔 Ingress로 노출
```

### Ingress

외부 트래픽을 클러스터 내부 Service로 라우팅한다. 도메인, HTTPS, 경로 기반 라우팅을 여기서 설정한다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend-ingress
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"  # 자동 HTTPS
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - example.com
      secretName: frontend-tls
  rules:
    - host: example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
```

### ConfigMap & Secret

환경 변수 주입에 사용한다. Gatsby나 Next.js의 환경 변수 파일(`.env`)을 컨테이너에 넣는 방법이다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: frontend-config
data:
  GATSBY_API_URL: "https://api.example.com"
  GATSBY_GITHUB_USERNAME: "gomsemarie"
```

```yaml
# Deployment에서 참조
envFrom:
  - configMapRef:
      name: frontend-config
```

단, Gatsby 같은 정적 사이트는 **빌드 시점**에 환경 변수가 번들에 포함된다. 런타임 주입이 의미 없다. 이 경우 이미지 빌드 시 `--build-arg`로 넘기거나, 런타임 환경 변수를 `window.__ENV__` 형태로 HTML에 주입하는 패턴을 쓴다.

```html
<!-- nginx가 렌더링하는 index.html에 동적 삽입 -->
<script>
  window.__ENV__ = {
    API_URL: "${API_URL}"
  };
</script>
```

```sh
# entrypoint.sh
envsubst < /usr/share/nginx/html/index.html > /tmp/index.html
cp /tmp/index.html /usr/share/nginx/html/index.html
nginx -g "daemon off;"
```

## HPA — 자동 스케일링

트래픽이 갑자기 몰릴 때 Pod를 자동으로 늘려준다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: frontend-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: frontend-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```

정적 사이트는 nginx가 워낙 가볍기 때문에 CPU가 60% 가는 경우가 드물긴 하다. 그래도 설정해두면 안심된다.

## 배포 파이프라인 흐름

```
개발자 push → GitHub Actions →
  [1] Docker 이미지 빌드
  [2] 이미지 레지스트리(ECR/GCR) push
  [3] kubectl set image로 Deployment 업데이트
  [4] Rolling Update 시작
  [5] Readiness Probe 통과하면 트래픽 전환
```

```yaml
# GitHub Actions 예시
- name: Deploy to Kubernetes
  run: |
    kubectl set image deployment/frontend-app \
      frontend=my-registry/frontend:${{ github.sha }} \
      --namespace=production
    kubectl rollout status deployment/frontend-app \
      --namespace=production \
      --timeout=5m
```

`kubectl rollout status`로 배포 완료를 기다린다. 실패하면 CI가 에러를 잡아준다.

## 롤백

배포 후 문제가 생기면 즉시 이전 버전으로 되돌릴 수 있다.

```bash
# 이전 버전으로 롤백
kubectl rollout undo deployment/frontend-app -n production

# 특정 리비전으로 롤백
kubectl rollout undo deployment/frontend-app --to-revision=3 -n production

# 배포 히스토리 확인
kubectl rollout history deployment/frontend-app -n production
```

이게 진짜 마음의 안정을 준다. 배포 잘못해도 10초 만에 되돌릴 수 있다.

## 내가 겪은 흔한 실수들

**1. `latest` 태그 사용**
`image: frontend:latest`는 절대 쓰지 마라. 어떤 버전인지 추적이 안 되고, 같은 태그여도 `imagePullPolicy`에 따라 다른 이미지를 쓸 수 있다. 항상 커밋 SHA나 버전 태그를 쓴다.

**2. readinessProbe 없음**
없으면 Pod가 완전히 준비되기 전에 트래픽이 들어와서 에러 응답이 나간다. nginx 기반이면 `/`에 200 응답 확인하는 readinessProbe는 기본으로 넣자.

**3. 리소스 limits 미설정**
프론트엔드 컨테이너는 가벼워서 그냥 두기 쉬운데, limits가 없으면 노드 리소스를 독차지할 수 있다. 작게라도 설정해두자.

**4. ConfigMap 변경 후 Pod 재시작 안 함**
ConfigMap을 바꿔도 이미 실행 중인 Pod에는 자동으로 반영되지 않는다. `kubectl rollout restart deployment/frontend-app`으로 재시작해야 한다.

---

K8s가 처음엔 진입 장벽이 높아 보이지만, 개념을 이해하면 오히려 배포가 더 안전하고 예측 가능해진다. 특히 롤링 업데이트와 롤백 기능은 한 번 써보면 이전으로 돌아가기 싫어진다.
