# Vercel 제대로 활용하기 — 프론트엔드 배포의 정석

처음 Vercel을 썼을 때 느낌은 "이게 배포라고?" 였다. GitHub 레포 연결하고 `Next.js` 프로젝트 올리면 끝이었다. 근데 실무에서 제대로 쓰다 보니 표면 아래에 엄청난 것들이 있었다. 이번 포스트에서는 그냥 배포 도구가 아닌, Vercel의 진짜 강점을 정리해봤다.

## Vercel이 어떻게 동작하는가

Vercel은 단순한 CDN + 호스팅이 아니다. 빌드-배포-실행이 통합된 플랫폼이다.

```
Git Push
  ↓
Vercel Build (프레임워크 자동 감지)
  ↓
┌─────────────────────────────────────────┐
│  Static Assets → CDN Edge (전 세계)       │
│  Server Functions → Serverless Functions│
│  Edge Middleware → Edge Runtime         │
└─────────────────────────────────────────┘
  ↓
사용자 요청 → 가장 가까운 엣지 POP에서 응답
```

이 구조 때문에 Vercel 배포는 보통 30초 안에 완료되고 전 세계 동시에 반영된다.

## Preview Deployments — 가장 사랑하는 기능

PR을 올리면 자동으로 고유한 URL을 가진 미리보기 환경이 생긴다. 팀 리뷰할 때 "이렇게 됩니다" 링크 하나 보내면 끝이다.

```
main branch  → production (example.com)
feature/XXX  → https://project-git-feature-xxx-team.vercel.app
```

Vercel 댓글 봇이 PR에 자동으로 Preview URL을 달아준다. 디자이너, 기획자, QA 모두 개발 환경 설정 없이 확인할 수 있다.

```yaml
# vercel.json — 특정 브랜치만 프로덕션으로 설정
{
  "github": {
    "autoAlias": true
  }
}
```

## Edge Middleware

요청이 서버에 닿기 전에 엣지에서 실행되는 코드다. 응답 시간에 거의 영향을 주지 않으면서 강력한 기능을 제공한다.

```ts
// middleware.ts (Next.js App Router 기준)
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;

  // A/B 테스트 — 쿠키로 버전 할당
  const bucket = request.cookies.get("ab-bucket")?.value;

  if (!bucket) {
    const newBucket = Math.random() < 0.5 ? "a" : "b";
    const response = NextResponse.next();
    response.cookies.set("ab-bucket", newBucket, { maxAge: 60 * 60 * 24 * 7 });
    return response;
  }

  // 인증 체크 — 로그인 페이지 리다이렉트
  const token = request.cookies.get("auth-token");
  if (pathname.startsWith("/dashboard") && !token) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  // 봇 차단
  const ua = request.headers.get("user-agent") ?? "";
  if (/bot|crawl|spider/i.test(ua) && pathname.startsWith("/admin")) {
    return new NextResponse(null, { status: 403 });
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/dashboard/:path*", "/admin/:path*"],
};
```

Edge Middleware는 엣지 런타임에서 실행되기 때문에 Node.js API 일부를 못 쓴다. `fs`, `crypto` 같은 것들은 제한된다. 대신 Web APIs(`fetch`, `Request`, `Response`)는 다 된다.

## Serverless Functions

Next.js의 API Routes나 독립적인 서버리스 함수를 배포할 수 있다.

```ts
// pages/api/og.tsx (Open Graph 이미지 동적 생성)
import { ImageResponse } from "@vercel/og";

export const config = {
  runtime: "edge", // Edge Runtime 사용
};

export default function handler(req: Request) {
  const { searchParams } = new URL(req.url);
  const title = searchParams.get("title") ?? "My Blog";

  return new ImageResponse(
    (
      <div
        style={{
          display: "flex",
          width: "1200px",
          height: "630px",
          background: "linear-gradient(to bottom right, #6d28d9, #4f46e5)",
          alignItems: "center",
          justifyContent: "center",
          padding: "60px",
        }}
      >
        <h1
          style={{
            color: "white",
            fontSize: "64px",
            fontWeight: "bold",
            textAlign: "center",
          }}
        >
          {title}
        </h1>
      </div>
    ),
    { width: 1200, height: 630 }
  );
}
```

이런 식으로 OG 이미지를 동적으로 만들 수 있다. 포스트 제목이 바뀌어도 이미지가 자동으로 생성된다.

## 환경 변수 관리

Vercel 대시보드에서 환경별 변수를 관리할 수 있다.

```
Production     →  NEXT_PUBLIC_API_URL=https://api.example.com
Preview        →  NEXT_PUBLIC_API_URL=https://staging-api.example.com
Development    →  NEXT_PUBLIC_API_URL=http://localhost:4000
```

Vercel CLI로 로컬에서도 Vercel 환경 변수를 당겨올 수 있다.

```bash
# Vercel 환경 변수를 .env.local로 가져오기
vercel env pull .env.local
```

팀 개발할 때 `.env` 파일을 공유하지 않아도 되니까 보안상으로도 좋다.

## Vercel Analytics

`@vercel/analytics` 패키지 하나 설치하면 실제 사용자 성능 지표를 볼 수 있다.

```tsx
// _app.tsx 또는 layout.tsx
import { Analytics } from "@vercel/analytics/react";
import { SpeedInsights } from "@vercel/speed-insights/next";

export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        {children}
        <Analytics />
        <SpeedInsights />
      </body>
    </html>
  );
}
```

Core Web Vitals (LCP, FID, CLS)를 실제 방문자 기반으로 수집해준다. Lighthouse 점수와 실제 사용자 경험이 다를 수 있는데, Analytics는 진짜 현장 데이터다.

## Cron Jobs (Pro 플랜)

주기적으로 실행되어야 하는 작업도 Vercel로 처리할 수 있다.

```json
// vercel.json
{
  "crons": [
    {
      "path": "/api/cron/revalidate",
      "schedule": "0 */6 * * *"
    }
  ]
}
```

```ts
// pages/api/cron/revalidate.ts
export default async function handler(req, res) {
  // Vercel이 Authorization 헤더로 보안 처리
  if (req.headers.authorization !== `Bearer ${process.env.CRON_SECRET}`) {
    return res.status(401).json({ error: "Unauthorized" });
  }

  // ISR 캐시 무효화
  await res.revalidate("/");
  await res.revalidate("/posts");

  res.json({ revalidated: true });
}
```

## ISR (Incremental Static Regeneration)

Next.js + Vercel 조합의 킬러 기능 중 하나다. 정적 사이트를 주기적으로 재생성한다.

```tsx
// Next.js Pages Router
export async function getStaticProps() {
  const posts = await fetchPosts();

  return {
    props: { posts },
    revalidate: 60, // 60초마다 백그라운드에서 재생성
  };
}
```

정적의 빠름 + 동적의 최신성을 동시에 갖는다. 단, Gatsby는 ISR이 없고 빌드 시점에 모두 생성된다. Gatsby로 블로그를 운영한다면 새 글마다 재배포해야 한다.

## 팀에서 Vercel 쓸 때 주의할 점

**1. 함수 실행 시간 제한**
Hobby 플랜은 10초, Pro는 60초, Enterprise는 900초다. 긴 작업은 백그라운드 잡으로 분리해야 한다.

**2. 번들 크기 제한**
Serverless Function은 250MB (압축 전)가 한도다. `sharp` 같은 네이티브 모듈은 크기를 확인해야 한다.

**3. Cold Start**
Serverless Function은 오래 안 쓰면 Cold Start 시간이 생긴다. Edge Runtime은 이 문제가 없다. 응답 시간이 중요한 엔드포인트는 Edge로 마이그레이션하는 걸 고려하자.

**4. 비용**
트래픽이 갑자기 몰리면 Serverless Function 실행 비용이 예상 밖으로 나올 수 있다. Spending Limit 설정을 꼭 해두자.

---

Vercel은 프론트엔드 개발자를 위해 설계된 플랫폼이다. 인프라 고민 없이 빠르게 시작하기에 최적이고, 점진적으로 복잡한 기능도 다 제공한다. Gatsby 블로그처럼 정적 사이트엔 사실 오버스펙이지만, Next.js 앱을 올릴 때는 진가를 발휘한다.
