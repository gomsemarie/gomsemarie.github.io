회사 ERP를 새 스택으로 옮기면서 화면도 새로 그렸다. 시안은 AI 디자인 도구인 Claude Design과 주고받으며 만들었는데, 첫 요청부터 18차까지 갔고 중간에 "15-1차"처럼 바로잡는 짧은 회차도 끼었다.

회차가 이만큼 쌓이면 대화창만으로는 관리가 안 된다. 무엇을 고쳐 달라고 했는지, 어떤 제안을 받았고 왜 뺐는지가 대화 스크롤 속에 묻힌다. 그래서 회차마다 프롬프트를 저장소의 파일로 남겼다. 프롬프트 초안은 AI 코딩 에이전트와 같이 고쳤고, 받은 시안을 화면에 반영하는 구현도 에이전트에게 맡겼다. 15~18차 근태·휴가 회차의 프롬프트 파일은 동료의 작업 브랜치에 같이 들어왔다.

## 회차마다 파일 하나

프롬프트는 `PROMPT.md`(1차), `PROMPT-2.md`부터 `PROMPT-18.md`까지 한 폴더에 둔다. 후속 수정은 `PROMPT-15-1.md`처럼 붙인다. 파일 맨 위에는 어디에 붙여 넣는지, 무엇을 첨부하는지를 적는다.

```md title="PROMPT-12.md (구조만 옮긴 예시)"
# 디자인 요청 프롬프트 (12차, 날짜)

아래를 디자인 도구 채팅에 그대로 붙여 넣는다. 11차(탭 바)를 이어서 다듬는 요청이다.

---

조건: 라이트 · 다크 모두, 지금 디자인 시스템 그대로, 화면마다 추천안 표시, Decision Log 에 기록.

① 화면 탭 바 다시 고르기 (11차 ② · D34 갱신)
② 페이지 하위 탭
```

파일로 두면 붙여 넣기 전에 에이전트와 같이 고칠 수 있다. 3차와 4차는 파일을 처음 만든 뒤에도 커밋이 두 번씩 더 있는데, "데이터 결과만 같으면 UI는 자유롭게 바꿔도 된다"는 문장이나 "모든 열 필터"를 나중에 끼워 넣었다. 11차 프롬프트는 엉뚱한 경로에 만들었다가 원래 폴더로 옮기고 10차 형식에 맞췄다. 형식이 같으면 다음 회차를 쓸 때 앞 파일을 열어 같은 틀로 시작할 수 있다.

10차부터는 머리말에 "이미 구현된 화면을 다듬는 시안"인지 "새로 만들 화면"인지 적었다. 이미 동작하는 화면은 구조를 지키고 모양만 다듬어 달라는 뜻이다. 화면에 따라 받아야 할 결과물도 다르다. 11차의 회사 테마에서는 색 값 21개 표가 가장 중요했고, 받은 표를 그대로 테마 설정의 색 칸에 옮길 수 있게 항목 이름까지 맞춰 달라고 했다.

## 고칠 것, 제안 채택 여부, 추가 화면

1차 프롬프트 끝에 "제안도 해 주세요" 절을 넣고 조건을 붙였다. 각 제안을 "무엇을 · 왜 · 참고 사례"로 짧게 쓰고, 기본 결과물과 분리해서 보여 주고, 데이터 저장 방식이나 업무 결과가 달라지는 제안이면 표시해 달라고 했다.

제안을 따로 받다 보니 2차부터는 답하는 틀이 생겼다.

```md title="PROMPT-2.md (구조만 옮긴 예시)"
## 1. 고칠 것
1. 다크 테마가 앱 화면에 적용되지 않는다. ...
2. 폰트 파일을 첨부했다. 로컬 파일로만 쓴다. ...

## 2. 제안 채택 여부
- 채택: A1, A2, ..., B3(편집 즉시 재계산 — 디바운스 500ms)
- C3: 채택하되 조건이 확실할 때만 표시
- B2: 보류. 이유 ...

## 3. 추가로 그려 줄 화면
1. 목록 + 상세 시트 ...
2. 마스터-디테일 ...
```

"고칠 것"은 시안의 결함, "제안 채택 여부"는 디자인 도구가 낸 아이디어에 대한 답, "추가 화면"은 다음 범위다. 이렇게 나눠 두면 무엇을 그대로 두고 무엇을 새로 그릴지가 바로 보여서, 앞 회차에서 좋았던 부분이 다음 시안에서 흐트러지지 않는다.

## 보류에는 이유를 쓴다

제안을 모두 받지는 않았고, 보류할 때는 이유를 같이 적었다. 이유를 적어 두지 않으면 다음 회차에 같은 제안이 다른 이름으로 다시 올라온다.

2차의 B2는 편집 중인 내용을 브라우저에 임시 저장하자는 제안이었다. 사용성만 보면 좋지만, 이 화면에서는 급여 값을 편집한다. 공용 PC에서 쓰면 브라우저 저장소에 민감정보가 남으니 보류하고 이번 시안에서 빼 달라고 했다.

4차에서는 "알림 · 내 할 일" 제안을 보류했다. 그때는 그 목록을 채울 실제 데이터가 없었고, 데이터 없이 그린 목록은 자리만 차지한다. "실제 데이터로 채울 수 있는 것만 남겨 달라"고 답했다.

> [!TIP]
> 조건을 붙여 채택하는 경우도 있었다. "한/영 상태 안내"는 채택하되, 입력기 조합 감지가 확실할 때만 표시하고 오탐이면 숨기게 했다. 받을지 말지 둘 중 하나로만 답했다면 이 제안은 빠졌을 것이다.

## D번호로 결정을 추적한다

디자인 도구에는 시안과 함께 Decision Log를 쓰게 했다. 결정마다 D번호를 붙이고 다음 내용을 적는다.

- 지금 형태가 어디서 왔는지(기존 ERP를 따른 것인지, 앞 시안인지, 새 기능인지)
- 영향: "업무 결과 같음", "저장 시점만 바뀜(값 같음)", "서버 · API 확인 필요" 중 하나
- 이전 → 이후, 이유, 검토한 대안

출처 칸은 3차에서 생겼다. 3차 프롬프트에서는 기존 ERP를 닮은 부분을 다시 따져 보라고 했다. 배치 하나하나가 기존을 따라서 그렇게 된 것인지, 더 나아서 고른 것인지 밝히라는 요청이었다. 이관하면서 지켜야 하는 것은 데이터를 다루는 결과이고, 버튼 위치까지 지킬 필요는 없었다.

영향 칸은 구현할 때 쓸모가 있었다. "업무 결과 같음"은 바로 반영하고, "서버 · API 확인 필요"는 백엔드부터 본다.

프롬프트에서도 D번호로 가리킨다. 12차는 "탭 바 다시 고르기(11차 ② · D34 갱신)"로 시작한다. 11차에서 탭 바 B안을 반영한 뒤 A안(크롬식)이나 D안(테두리 탭)이 더 낫다는 의견이 나와서, 12차에서 두 안을 실제 크기로 다시 비교해 달라고 했다. 바로 아래 페이지 하위 탭과 한 화면에 놓였을 때 위계가 분명한지를 기준으로 삼아 달라는 말도 적었다.

## 반영 커밋과 회차를 잇는다

반영 커밋 제목은 회차와 D번호로 시작한다.

```text title="git log (형식만 옮긴 예시)"
디자인 11차 반영: 탭 바 B(D34 — 36px · 선택 탭 면이 내용과 이어짐 …) / 진행 표시(D37 …) / AI 다듬기(D35 …)
디자인 12차 반영: 메인 탭 A 크롬식(높이 31 · 윗모서리 6 …) / 페이지 하위 탭(D38 b): …
요청 창구 개편(디자인 13 · 14차, D39 ~ D43): …
```

이렇게 해 두면 `git log --grep D34`로 그 결정이 언제 어떻게 바뀌었는지 따라갈 수 있다. 앞에서 말한 탭 바가 B에서 A로 바뀐 과정도 두 커밋에 남아 있다.

구현 쪽에도 기록을 하나 더 둔다. 결정 목록 문서의 "디자인과 다른 점" 표에, 시안에 있지만 API에 칸이 없어서 넣지 않은 것이나 시안의 블러 대신 꽉 찬 가림 칸을 쓴 것 같은 차이를 이유와 함께 적는다. 시안과 구현이 다를 때 어느 쪽이 실수인지 바로 알 수 있다.

## 디자인 도구가 정한 규칙은 바로잡는다

15차 근태 · 휴가 시안은 화면만 그리지 않고 "2일 이하면 부서장 결재" 같은 일수 분기로 결재 규칙까지 정해서 그렸다. 그럴듯했지만 회사 규칙은 아니었다.

그래서 16차로 넘어가기 전에 15-1차를 짧게 보냈다. 결재선은 일수 분기 없이 하나로, 지각 유예는 기본 0분으로, 대결자는 옵션으로 두되 기본은 끈다는 내용이다. Decision Log에서 시안이 정했던 규칙 항목은 "회사 기준으로 바뀜"으로 고치고, 이후 회차도 이 기준을 따르라고 적었다. 기록에 틀린 규칙이 남아 있으면 다음 회차 시안이 그 규칙을 다시 근거로 쓰기 때문이다.

> [!WARNING]
> 디자인 도구는 업무 규칙을 주지 않으면 그럴듯한 규칙을 지어 화면에 넣는다. 화면이 그럴듯해 보여도 그 규칙이 회사 기준인지는 따로 확인해야 했다.

7차에서도 비슷한 일이 있었다. 6차 결과에서 디자인 도구가 "이번에는 화면을 직접 띄워 보지 못했다"고 해서, 7차 첫 항목을 "모든 상태를 라이트 · 다크로 직접 띄워 깨진 곳을 고쳐 달라"로 잡았다. 14차에서는 좁은 카드 안의 글자가 한 글자씩 세로로 접힌 곳을 "깨진 곳"으로 따로 짚었다.

## 정리

- 회차마다 프롬프트를 파일로 남겼다. 붙여 넣기 전에 고칠 수 있고, 앞 회차 형식을 그대로 이어 쓸 수 있다.
- 2차부터 "고칠 것 · 제안 채택 여부 · 추가 화면"으로 나눠 답해서 결함 수정과 새 범위를 섞지 않았다.
- 보류에는 이유를 적었다. 편집 중 임시 저장은 공용 PC에 민감정보가 남을 수 있어 보류했다.
- 결정은 D번호로 추적하고 출처와 영향(업무 결과 같음 · 저장 시점만 바뀜 · API 확인 필요)을 함께 적었다.
- 반영 커밋 제목에 회차와 D번호를 넣어 결정이 바뀐 과정을 `git log`로 따라갈 수 있게 했다.
- 디자인 도구가 지어낸 업무 규칙은 다음 회차 전에 바로잡고, 기록에서도 고쳤다.
