## 올리는 값이 돌리는 값을 압도했다

[앞 글](/posts/sandboxed-rule-runner/)에서 룰을 요청당 워커 하나에서 돌리게 했다. 워커는 메시지를 받을 때마다 룰셋을 통째로 vm 컨텍스트에 올리고, 일이 끝나면 부모가 죽인다. 화면 하나를 변환할 때는 문제가 없었다. 예열해 두면 사용자는 기동 비용을 느끼지 않는다.

문제는 짧은 원본을 많이 돌릴 때 생겼다. 룰마다 예시 코드를 붙이고, 그 룰만 켜서 예시를 돌려 보는 검사를 만들고 있었다. 예시는 몇 줄짜리다. 하나씩 보내면 예시 수만큼 룰셋을 다시 올린다. 몇 줄을 변환하는 값보다 룰셋 하나 올리는 값이 훨씬 컸다.

실측은 이랬다. 같은 룰셋으로 예시 8개를 하나씩 돌리니 883ms였다. 34개면 약 3,753ms로 늘어난다. 이 상태로 두면 예시 기반 검사가 기존 표본 검증보다 느려진다. 이 작업은 AI 코딩 에이전트와 함께 했다.

## 한 워커에서 여러 건

워커에 `convert-many`라는 통로를 하나 더 냈다. 룰셋은 한 번만 올리고, 일마다 켤 룰 목록을 바꿔 가며 돈다. 일마다 켤 룰이 다르다는 점이 이 통로가 필요한 이유다. 같은 원본을 여러 번 도는 것이 아니라 룰마다 자기 예시를 자기만 켜고 돈다.

```ts title="worker.ts"
function runMany(job: ManyJob) {
  const loaded = loadRuleFiles(job.support, job.rules); // 한 번만 올린다
  const all = loaded.registry.list();

  const items = job.jobs.map((one) => {
    const active = one.enabled ? all.filter((r) => one.enabled!.includes(r.id)) : all;
    try {
      return { key: one.key, ...convert(one.source, active) };
    } catch (e) {
      // 이 한 건만 접고 계속 간다
      return { key: one.key, output: one.source, parseError: String(e) };
    }
  });

  port.postMessage({ type: 'done-many', items });
}
```

34개를 한꺼번에 돌리니 169ms였다. 앞의 추정치와 비교해 22배다. 3,753ms는 8개 실측을 34개로 늘려 잡은 값이고, 169ms는 34개를 실제로 잰 값이다.

이 숫자에는 쓸모가 하나 더 있었다. 화면 시안을 요청하면서 "재 보고 1.5초를 넘으면 그때 진행 표시를 청하겠다"고 적어 둔 적이 있다. 169ms면 `21 / 34` 같은 진행 표시가 필요 없다. 그리지 않아도 되는 화면 하나가 줄었다.

## 격리는 그대로인가

요청당 워커 하나를 고집한 이유가 전역 오염 격리였다. 한 워커에서 여러 건을 돌면 그 원칙을 깨는 것처럼 보인다.

구분해야 할 것이 있다. 위험한 것은 앞 요청의 전역이 다음 요청으로 새는 일이다. 다른 사람이 켠 룰, 다른 화면의 표가 남는다. 배치는 한 요청 안에서 같은 룰셋을 여러 원본에 돌릴 뿐이다. 이 워커도 일이 끝나면 부모가 죽인다. 워커를 재사용하지 않는다는 원칙은 그대로다.

다만 한 요청 안에서도 일마다 다른 화면 정보를 깔아야 했다. 화면이 있어야 일하는 룰이 있어서다. 룰셋은 그대로 두고 전역만 갈아 끼운다. 이때 앞 일이 깔아 둔 값은 지워야 한다. 안 지우면 "목록이 없으면 건너뛴다" 같은 룰이 남의 목록을 본다.

```ts title="worker.ts"
// 어떤 열쇠들이 일마다 바뀌는지 먼저 다 모은다
const keys = new Set(job.jobs.flatMap((j) => Object.keys(j.globals ?? {})));

function setWorld(mine: Record<string, unknown> = {}) {
  for (const k of keys) {
    if (k in mine) loaded.context[k] = mine[k];
    else delete loaded.context[k]; // 앞 일이 깔아 둔 것을 지운다
  }
}
```

전역은 일과 일 사이에만 바꾼다. 룰이 도는 도중에 바꾸면 그 룰은 반은 옛 화면, 반은 새 화면을 본다.

## 배치에만 다르게 한 것

배치는 검사용 통로다. 그래서 일반 변환과 세 군데를 다르게 했다.

첫째, 재시도가 없다. 일반 변환은 룰 하나가 터지면 그 룰만 빼고 다시 돌려 결과를 건진다. 검사에서 그렇게 하면 터진 룰을 빼고 통과시키는 셈이다. 검사가 눈감아 준 것이 된다.

둘째, 하나가 터져도 멈추지 않는다. 서른 개를 보다가 하나에서 멈추면 고칠 것이 하나인지 서른인지 모른다. 터진 자리는 그 건의 `parseError`로 남기고 계속 간다.

셋째, 시간 상한을 건수만큼 늘린다. 한 건짜리 상한을 그대로 쓰면 서른 건을 도는 순간 늘 걸린다. 룰셋 적재는 한 번뿐이라 건당 상한에 여유 한 번을 더했다.

```ts title="runner.ts"
const budget = timeoutMs * (job.jobs.length + 1);
```

## 회귀 검증을 여러 줄로

같은 날 다른 쪽에서도 느린 곳이 드러났다. 룰셋을 바꾸기 전에 최근 변환 표본을 새 룰셋으로 다시 돌려 보는 회귀 검증이다. 다음 글에서 자세히 다룬다.

검증은 표본마다 워커를 세 번 돌린다. 결과 비교 한 번, 두 번 돌려 같은지 보는 시험 두 번이다. 표본 30건이면 워커 90번이다. 이걸 한 줄로 세워 하나씩 기다리고 있었다. 400줄짜리 화면 스크립트에 룰이 서른몇 개면 수 초가 걸렸다. 그동안 화면은 아무 말도 하지 않았다. 사람들은 버튼이 안 먹은 줄 알고 다시 눌렀다.

그래서 표본을 여러 줄로 나눠 돌렸다. 표본 12건, 같은 원본으로 쟀다.

| 줄 수 | 걸린 시간 | 비고 |
| --- | --- | --- |
| 1 (전) | 11,720ms | |
| 4 (지금) | 3,317ms | 3.5배 |
| 8 | 3,028ms | 거의 안 줄어듦 |

## 상한이 없으면 워커 90개

처음 떠오르는 구현은 `Promise.all(samples.map(check))`다. 여기서는 그러면 안 된다.

검증용 실행기는 예열 워커를 두지 않는다. 가끔 도는 일이라 데워 둘 이유가 없다. 그래서 부를 때마다 워커를 새로 띄우고, 끝나면 죽인다. 실행기에는 풀 상한이 없다. 표본을 전부 한꺼번에 풀면 워커 90개가 동시에 뜬다.

상한은 부르는 쪽이 쥔다. 정해진 수의 줄이 커서 하나를 나눠 쓰며 표본을 하나씩 가져간다.

```ts title="lanes.ts"
export async function inLanes<T, R>(items: T[], lanes: number, work: (t: T) => Promise<R>) {
  const out = new Array<R>(items.length);
  let cursor = 0;
  await Promise.all(
    Array.from({ length: Math.min(lanes, items.length) }, async () => {
      for (;;) {
        const i = cursor++;
        if (i >= items.length) return;
        out[i] = await work(items[i]); // 끝난 순서가 아니라 자기 자리에 넣는다
      }
    }),
  );
  return out;
}
```

결과를 바깥 배열에 `push`하지 않고 자기 자리에 넣는 것도 의도한 것이다. `push`하면 끝난 순서대로 쌓인다. 같은 룰셋을 두 번 검사했는데 사유가 다른 차례로 나오면, 사람은 무언가 또 바뀐 줄 안다.

시험에서는 줄 수를 1로 고정한다. 시험이 확인하려는 것은 빠르기가 아니라 결과다. 여럿이 겹쳐 돌면 워커가 늘어 시험 전체가 느려진다.

## 8줄은 왜 안 빨랐나

워커 하나는 룰셋을 통째로 올린다. 메모리를 꽤 쓴다. 줄을 늘린다고 계속 빨라지지 않고, 어느 지점부터는 서로 밀어낸다. 4줄과 8줄의 차이가 300ms 정도였다.

그리고 이 서버는 팀이 같이 쓴다. 검증이 도는 동안에도 다른 사람은 변환을 한다. 검증을 빠르게 하자고 그 사람들의 변환이 멈추면 바꾸지 않은 것만 못하다. 그래서 기본값을 "코어 수에서 하나를 빼고, 넷을 넘기지 않는다"로 잡았다.

```ts title="lanes.ts"
import { availableParallelism } from 'node:os';

export const defaultLanes = () => Math.max(1, Math.min(4, availableParallelism() - 1));
```

> [!NOTE]
> 표의 수치는 같은 원본, 같은 룰셋으로 한 자리에서 잰 것이다. 코어 수와 룰셋 크기가 다르면 꺾이는 지점도 다르다. 상한을 숫자로 박지 않고 코어 수에 묶은 이유다.

## 정리

- 요청당 워커 구조에서는 짧은 원본일수록 룰셋 적재 비용이 실행 비용을 압도한다.
- `convert-many`로 룰셋을 한 번만 올리고 일마다 켤 룰과 전역만 갈아 끼웠다. 예시 34개가 169ms다.
- 한 요청 안에서 여러 번 도는 것과 워커를 재사용하는 것은 다르다. 워커는 여전히 일이 끝나면 죽는다.
- 검사용 배치에는 재시도가 없고, 하나가 터져도 멈추지 않으며, 시간 상한을 건수만큼 늘린다.
- 회귀 검증은 4줄로 나눠 11.7초에서 3.3초가 됐다. 8줄은 거의 이득이 없었다.
- 실행기에 풀 상한이 없으면 부르는 쪽이 상한을 쥔다. 결과는 끝난 순서가 아니라 목록 순서로 모은다.
