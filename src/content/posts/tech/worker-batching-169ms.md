## 올리는 비용이 돌리는 비용보다 컸다

[앞 글](/posts/sandboxed-rule-runner/)에서 룰을 요청당 워커 하나에서 돌리게 했다. 워커는 메시지를 받을 때마다 룰셋을 통째로 vm 컨텍스트에 올리고, 일이 끝나면 부모가 죽인다. 화면 하나를 변환할 때는 문제가 없었다. 예열해 두면 사용자는 기동 비용을 느끼지 못한다.

문제는 짧은 원본을 많이 돌릴 때 생겼다. 그때 룰마다 예시 코드를 붙이고, 그 룰만 켜서 예시를 돌려 보는 검사를 만들고 있었다. 예시는 몇 줄짜리라서 하나씩 보내면 예시 수만큼 룰셋을 다시 올리게 된다. 몇 줄을 변환하는 비용보다 룰셋 하나를 올리는 비용이 훨씬 컸다.

같은 룰셋으로 예시 8개를 하나씩 돌리니 883ms가 걸렸다. 34개면 약 3,753ms로 늘어난다. 그대로 두면 예시 기반 검사가 기존 표본 검증보다 느려질 판이었다.

## 한 워커에서 여러 건

워커에 `convert-many`라는 통로를 하나 더 냈다. 룰셋은 한 번만 올리고, 일마다 켤 룰 목록을 바꿔 가며 돈다. 이 통로가 따로 필요했던 것은 일마다 켤 룰이 다르기 때문이다. 같은 원본을 여러 번 도는 일은 없고, 룰마다 자기 예시를 자기만 켠 채로 돈다.

```ts title="worker.ts"
function runMany(job: ManyJob) {
  const loaded = loadRuleFiles(job.support, job.rules); // 한 번만 올린다
  const all = loaded.registry.list();

  const items = job.jobs.map((one) => {
    const active = one.enabled ? all.filter((r) => one.enabled!.includes(r.id)) : all;
    try {
      return { key: one.key, ...convert(one.source, active) };
    } catch (e) {
      // 이 한 건만 접고 계속 간다
      return { key: one.key, output: one.source, parseError: String(e) };
    }
  });

  port.postMessage({ type: 'done-many', items });
}
```

34개를 한꺼번에 돌리니 169ms였다. 앞의 추정치보다 22배 빠르다. 3,753ms는 8개 실측값을 34개로 늘려 잡은 값이고, 169ms는 34개를 실제로 잰 값이다.

이 숫자는 화면 쪽에도 쓸모가 있었다. 화면 시안을 요청하면서 "재 보고 1.5초를 넘으면 그때 진행 표시를 청하겠다"고 적어 둔 적이 있다. 169ms면 `21 / 34` 같은 진행 표시가 필요 없으니, 그릴 화면이 하나 줄었다.

## 격리는 그대로인가

요청당 워커 하나를 고집한 이유는 전역 오염 격리였다. 한 워커에서 여러 건을 돌면 그 원칙을 깨는 것처럼 보인다.

여기서 구분할 것이 있다. 위험한 것은 앞 요청의 전역이 다음 요청으로 새는 일이다. 다른 사람이 켠 룰이나 다른 화면의 표가 남는 경우다. 배치는 한 요청 안에서 같은 룰셋을 여러 원본에 돌릴 뿐이고, 이 워커도 일이 끝나면 부모가 죽인다. 워커를 재사용하지 않는다는 원칙은 그대로다.

다만 한 요청 안에서도 일마다 다른 화면 정보를 깔아야 했다. 화면 정보가 있어야 일하는 룰이 있기 때문이다. 룰셋은 그대로 두고 전역만 갈아 끼운다. 이때 앞 일이 깔아 둔 값은 지워야 한다. 지우지 않으면 "목록이 없으면 건너뛴다" 같은 룰이 다른 일의 목록을 보게 된다.

```ts title="worker.ts"
// 어떤 열쇠들이 일마다 바뀌는지 먼저 다 모은다
const keys = new Set(job.jobs.flatMap((j) => Object.keys(j.globals ?? {})));

function setWorld(mine: Record<string, unknown> = {}) {
  for (const k of keys) {
    if (k in mine) loaded.context[k] = mine[k];
    else delete loaded.context[k]; // 앞 일이 깔아 둔 것을 지운다
  }
}
```

전역은 일과 일 사이에서만 바꾼다. 룰이 도는 도중에 바꾸면 그 룰은 반은 옛 화면을, 반은 새 화면을 보게 된다.

## 배치에서만 다르게 한 것

배치는 검사용 통로라서 일반 변환과 세 군데를 다르게 했다.

먼저 재시도가 없다. 일반 변환은 룰 하나가 터지면 그 룰만 빼고 다시 돌려 결과를 건진다. 검사에서 그렇게 하면 터진 룰을 빼고 통과시키게 되고, 검사가 문제를 덮어 버린다.

하나가 터져도 멈추지 않는다. 서른 개를 보다가 하나에서 멈추면 고칠 것이 하나인지 서른인지 알 수 없다. 터진 자리는 그 건의 `parseError`로 남기고 다음 건으로 간다.

시간 상한은 건수만큼 늘린다. 한 건짜리 상한을 그대로 쓰면 서른 건을 도는 순간 늘 걸린다. 룰셋 적재는 한 번뿐이라 건당 상한에 여유분 한 번을 더했다.

```ts title="runner.ts"
const budget = timeoutMs * (job.jobs.length + 1);
```

## 회귀 검증을 여러 줄로

같은 날 다른 곳에서도 느린 데가 드러났다. 룰셋을 바꾸기 전에 최근 변환 표본을 새 룰셋으로 다시 돌려 보는 회귀 검증이다. 이 검증 자체는 다음 글에 자세히 적는다.

검증은 표본마다 워커를 세 번 돌린다. 결과 비교에 한 번, 두 번 돌려 결과가 같은지 보는 시험에 두 번이다. 표본이 30건이면 워커를 90번 띄운다. 이걸 한 줄로 세워 하나씩 기다리고 있었다. 400줄짜리 화면 스크립트에 룰이 서른몇 개면 수 초가 걸렸고, 그동안 화면에는 아무 표시도 없었다. 사람들은 버튼이 안 눌린 줄 알고 다시 눌렀다.

그래서 표본을 여러 줄로 나눠 돌렸다. 같은 원본으로 표본 12건을 재 봤다.

| 줄 수 | 걸린 시간 | 비고 |
| --- | --- | --- |
| 1 (전) | 11,720ms | |
| 4 (지금) | 3,317ms | 3.5배 |
| 8 | 3,028ms | 거의 안 줄어듦 |

## 상한이 없으면 워커가 90개 뜬다

처음 떠오르는 구현은 `Promise.all(samples.map(check))`인데, 여기서는 그렇게 하면 안 된다.

검증용 실행기는 예열 워커를 두지 않는다. 가끔 도는 일이라 미리 띄워 둘 이유가 없어서, 부를 때마다 워커를 새로 띄우고 끝나면 죽인다. 그리고 이 실행기에는 풀 상한이 없다. 표본을 한꺼번에 다 풀면 워커 90개가 동시에 뜬다.

그래서 상한은 부르는 쪽에서 정한다. 정해진 수의 줄이 커서 하나를 같이 쓰면서 표본을 하나씩 가져간다.

```ts title="lanes.ts"
export async function inLanes<T, R>(items: T[], lanes: number, work: (t: T) => Promise<R>) {
  const out = new Array<R>(items.length);
  let cursor = 0;
  await Promise.all(
    Array.from({ length: Math.min(lanes, items.length) }, async () => {
      for (;;) {
        const i = cursor++;
        if (i >= items.length) return;
        out[i] = await work(items[i]); // 끝난 순서가 아니라 자기 자리에 넣는다
      }
    }),
  );
  return out;
}
```

결과를 바깥 배열에 `push`하지 않고 원래 자리에 넣은 것도 일부러 그렇게 했다. `push`하면 끝난 순서대로 쌓인다. 같은 룰셋을 두 번 검사했는데 사유가 다른 순서로 나오면, 보는 사람은 뭔가 또 바뀐 줄 안다.

시험에서는 줄 수를 1로 고정한다. 시험으로 확인하려는 것은 결과이고 속도는 상관없다. 여럿이 겹쳐 돌면 워커가 늘어 시험 전체가 오히려 느려진다.

## 8줄은 왜 더 빠르지 않았나

워커 하나가 룰셋을 통째로 올리기 때문에 메모리를 꽤 쓴다. 줄을 늘린다고 계속 빨라지지 않고, 어느 지점부터는 서로 자원을 다툰다. 4줄과 8줄의 차이는 300ms 정도였다.

또 이 서버는 팀이 같이 쓴다. 검증이 도는 동안에도 다른 사람은 변환을 한다. 검증을 빠르게 하느라 그 사람들의 변환이 멈추면 안 하느니만 못하다. 그래서 기본값을 "코어 수에서 하나를 빼고, 넷을 넘기지 않는다"로 잡았다.

```ts title="lanes.ts"
import { availableParallelism } from 'node:os';

export const defaultLanes = () => Math.max(1, Math.min(4, availableParallelism() - 1));
```

> [!NOTE]
> 표의 수치는 같은 원본, 같은 룰셋으로 한 자리에서 잰 값이다. 코어 수와 룰셋 크기가 다르면 꺾이는 지점도 달라진다. 상한을 고정된 숫자로 두지 않고 코어 수에 묶은 이유다.

## 정리

- 요청당 워커 구조에서는 원본이 짧을수록 룰셋을 올리는 비용이 실행 비용보다 커진다.
- `convert-many`로 룰셋을 한 번만 올리고 일마다 켤 룰과 전역만 갈아 끼웠다. 예시 34개를 도는 데 169ms가 걸린다.
- 한 요청 안에서 여러 번 도는 것은 워커 재사용과 다르다. 워커는 여전히 일이 끝나면 죽는다.
- 검사용 배치에는 재시도가 없고, 하나가 터져도 멈추지 않으며, 시간 상한을 건수만큼 늘린다.
- 회귀 검증은 4줄로 나눠 11.7초에서 3.3초로 줄었다. 8줄로 늘려도 거의 나아지지 않았다.
- 실행기에 풀 상한이 없으면 부르는 쪽이 상한을 정한다. 결과는 끝난 순서대로 모으지 않고 목록 순서대로 모은다.
