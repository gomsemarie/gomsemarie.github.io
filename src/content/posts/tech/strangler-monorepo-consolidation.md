## 어떤 IDE인가

회사에서 노코드 UI 빌더를 만들고 있다. 이 시리즈는 그 빌더를 담는 데스크톱 IDE 이야기다. Electron 앱이고, 한 창 안에 파일 탐색기, Monaco 코드 에디터, 빌더 화면이 들어간다. 패널은 dockview로 붙였다 떼었다 할 수 있다. VSCode와 비슷한 모양에 화면 빌더를 얹었다고 보면 된다.

저장소는 yarn 워크스페이스 모노레포다. IDE 말고도 빌더로 만든 화면을 실행하는 뷰어, 다른 업무용 웹 앱, Electron 뷰어가 같은 저장소에 있고 공통 패키지를 함께 쓴다.

첫 글은 구조 정리다. 기능을 더 붙이기 전에 패키지 경계부터 다시 그어야 했다.

## 그 전 단계: feature 기반 구조

2025년 10월에 IDE 패키지를 한 번 정리했다. 그때까지 코드는 `pages/ide/` 아래에 쌓여 있었다. 화면 하나의 폴더 안에 위젯 설정, 위젯 컴포넌트, 탭 헤더, 에디터 컴포넌트가 다 들어 있었다.

이것을 feature 기반으로 옮겼다. 코드 에디터에 속한 것은 `features/code-editor/` 아래 `components/tab-contents`, `components/tab-headers`, `components/extensions`, `constants`, `types`로 나눴다. 여러 곳에서 쓰는 것은 `shared/`로, 당장 쓰지 않지만 지우기 아까운 위젯 설정은 `archive/`로 보냈다. 139개 파일이 바뀌었다.

이번 글의 작업은 이 기준을 패키지 단위로 넓힌 것이다.

## 문제: IDE가 두 개, 공통 코드도 두 군데

시간이 지나며 구조가 다시 꼬였다. 새 IDE를 `ide-new`라는 별도 패키지로 만들기 시작했고, 옛 `ide` 패키지가 그대로 남았다. 새 IDE 쪽에는 토스트, 오버레이, 컨텍스트 메뉴, 단축키, 커맨드 팔레트 같은 공통 시스템이 잘 정리돼 있었다. 그런데 그것들은 IDE 안에 있어서 뷰어나 다른 앱이 쓸 수 없었다. 반대로 공통 패키지에는 오래된 같은 기능이 따로 있었다. 스플래시, 시스템 알림, 코드 에디터, shadcn ui 컴포넌트가 양쪽에 중복으로 있었다.

목표는 이렇게 잡았다.

- 옛 IDE를 지우고 새 IDE를 `ide`로 부른다.
- IDE 안의 도메인과 무관한 공통 시스템을 공통 패키지로 올린다.
- 중복은 새 IDE 쪽을 표준으로 정리한다.
- 공통 패키지 내부 구조(`shared/`, `features/`)를 평평하게 만든다.

한 번에 다 옮기면 빌드가 언제 깨졌는지 알 수 없다. 그래서 Strangler 방식으로 갔다. 새 자리를 만들고, 한 모듈씩 옮기고, 옛 자리는 새 자리를 가리키게 두었다가 마지막에 걷어 낸다.

작업은 AI 코딩 에이전트와 함께 했다. 단계마다 에이전트가 계획을 내면 내가 확인하고 승인하는 식이었다. 커밋은 하루 오전에 몰려 있다.

## Phase 1A: 옛 IDE 지우기

먼저 옛 `ide` 디렉토리를 지우고 `ide-new`를 `ide`로 바꿨다. 이름만 바꾸면 끝나지 않는다. import alias(`@ide-new/`), 프로젝트 스키마 URI, Electron appId, 프로젝트 로컬 설정 폴더 이름(`.ide-new/`)까지 문자열이 흩어져 있었다. 추적 중인 거의 모든 텍스트 파일 확장자를 대상으로 일괄 치환했다.

```sh title="phase-1a-codemod.sh"
# 긴 패턴부터 바꿔야 짧은 패턴이 먼저 먹는 일을 막는다
git ls-files '*.ts' '*.tsx' '*.json' '*.md' '*.css' '*.yml' \
  | xargs sed -i \
      -e 's#@ide-new-electron/#@ide-electron/#g' \
      -e 's#@ide-new/#@ide/#g' \
      -e 's#ide-new://#ide://#g' \
      -e 's#\.ide-new/#.ide/#g' \
      -e 's#ide-new#ide#g'
```

치환하고 나면 `ide|ide`처럼 같은 말이 두 번 붙은 곳이 생겨서 그것도 정리했다. 631개 파일이 바뀌었고 삭제가 3만 6천 줄을 넘었다. 빌드는 통과했다. 타입 오류가 네 건 있었지만 모두 이전부터 있던 것이라 이 작업과 구분해 기록해 두었다.

## Phase 1B: 소비처를 세서 순서를 정했다

옮기기 전에 공통 패키지의 각 영역을 누가 얼마나 쓰는지 셌다. 패키지별 import 수를 표로 만들었다.

| 영역 | 뷰어 | 업무 앱 | IDE | 내부 | 판단 |
|---|---:|---:|---:|---:|---|
| api | 8 | 41 | 0 | 2 | 업무 앱 전용 |
| hoc | 2 | 13 | 0 | 0 | 업무 앱 전용 의심 |
| utils | 7 | 16 | 10 | 16 | IDE 의존이 크다 |
| hof | 0 | 0 | 0 | 2 | 외부 사용 없음 |
| view-system | 0 | 0 | 0 | 0 | 쓰지 않음 |

이 표로 영역을 다섯 갈래로 나눴다.

- **유지**: 빌더 코어와 위젯. 빌더 코어는 따로 협의하기 전에는 건드리지 않는 보호 영역으로 정했다.
- **이전**: 도메인과 무관한 IDE 쪽 공통 시스템. 토스트, 이벤트 버스, 오버레이, 컨텍스트 메뉴 등.
- **재배치**: 특정 앱만 쓰는 것. 그 앱 패키지로 보낼 후보.
- **중복 정리**: 스플래시, 시스템 알림, 코드 에디터, shadcn ui. IDE 쪽을 표준으로.
- **삭제**: 외부 사용이 0인 것. 내부 역참조를 확인한 뒤 지운다.

첫 이전 대상은 store 생성 유틸리티로 정했다. Provider 범위 store를 만드는 함수로, 다른 store 모듈들이 모두 이것을 쓴다. 바닥에 있는 것을 먼저 옮겨야 위에 있는 것을 옮길 때 경로가 꼬이지 않는다. 파일 하나에 150줄 정도라 이 방식이 통하는지 확인하기에도 알맞았다. 그다음 순서는 의존 방향을 따라 작은 유틸, 상수, 이벤트 버스, 토스트, 알림 순으로 잡았다.

> [!TIP]
> 사용량 표는 이전 순서뿐 아니라 "옮기지 않을 것"을 정하는 데도 쓸모가 있었다. 외부 사용이 0인 영역은 옮길 필요 없이 지우면 되고, 한 앱만 쓰는 영역은 공통에 둘 이유가 없다.

## Phase 1C: 임시 경유지와 re-export wrapper

공통 패키지 안에 `core/`라는 새 자리를 만들었다. 처음부터 임시라고 정한 자리다. 옮기는 동안 쓰고, 끝나면 없앤다.

모듈 하나를 옮기는 절차는 같았다.

1. 본체를 `core/` 아래로 옮긴다.
2. 옛 자리에는 새 자리를 다시 내보내는 wrapper만 남기고 `@deprecated`를 단다.
3. IDE, 뷰어, 업무 앱을 빌드한다.
4. 커밋한다.

```ts title="shared/utils/create-scoped-store.ts"
/**
 * @deprecated 새 코드는 '@common/core/utils/create-scoped-store'에서 가져온다.
 * import 경로 일괄 교체(Phase 2) 뒤 이 파일은 지운다.
 */
export * from '@common/core/utils/create-scoped-store';
```

wrapper 덕분에 사용처는 이 단계에서 바뀌지 않는다. 빌드가 깨지면 원인은 방금 옮긴 모듈 하나다. 1C-1부터 1C-18까지 이렇게 옮겼고, 강하게 엮인 모듈은 묶어서 옮겼다. 마지막에는 공통 패키지의 옛 스플래시와 시스템 알림에 deprecate 표시를 했다.

## Phase 2: import 경로 cutover

모든 모듈이 경유지에 모인 뒤 사용처의 import를 새 경로로 바꿨다. 먼저 IDE 내부의 `@ide/features/...` import를 `@common/core/features/...`로 바꾸고 IDE 쪽 wrapper를 지웠다. 159개 파일이 바뀌었다.

예외가 하나 남았다. 이벤트 버스의 Electron 브리지는 Electron에 묶여 있어서 IDE에 두었다. IDE의 이벤트 버스 진입점은 공통 이벤트 버스를 그대로 내보내면서 브리지 함수만 하나 더 내보낸다.

그다음 뷰어와 공통 내부의 사용처를 바꿨다. 빌더 코어의 store 파일 다섯 개는 보호 영역이라 바로 바꾸지 않고 wrapper를 유지했다. 확인을 받은 뒤 경로만 바꿨고 로직은 건드리지 않았다. 사용처가 하나도 남지 않은 것을 확인하고 공통 쪽 wrapper까지 지웠다.

## Phase 3: 경유지 폐지와 워크스페이스 분리

경로가 정리되자 패키지 경계를 다시 그었다.

- **위젯 워크스페이스 신설**: 빌더 코어, 그리드, 위젯 카탈로그를 공통에서 꺼내 `widget` 패키지로 옮겼다. 층은 `common → widget → 앱`이 됐다. 공통 타입 barrel이 위젯 쪽 타입을 내보내던 줄은 지웠다. 공통이 위젯에 의존하면 층이 거꾸로 된다.
- **`core/` 폐지**: 경유지에 있던 `utils`, `constants`, `types`, `components`, `features`를 공통 패키지 바로 아래로 올리고, `@common/core/*`를 `@common/*`로 바꿨다. 경유지는 계획대로 사라졌다.
- **`shared/` 폐지**: 남은 `api`, `hooks`, `stores`, `styles`, `types`, `utils`도 한 단계 위로 올렸다. 두 군데 있던 `utils/index.ts`는 하나로 합쳤다. SCSS `additionalData`와 CSS `@import`에 적힌 경로도 함께 바꿔야 했다.
- **Electron 워크스페이스 분리**: Electron 공통 코드는 처음에 공통 패키지 안으로 흡수했다. 그런데 그러자 `@parcel/watcher`, `@vscode/ripgrep`, `fdir` 같은 main process 전용 native 모듈이 공통 패키지의 의존성이 됐다. 뷰어나 업무 앱 같은 웹 앱까지 이것을 끌고 갔다. 그래서 `electron` 워크스페이스를 따로 만들고 main, preload, renderer 코드와 native 의존성을 옮겼다. 공통 패키지는 플랫폼과 무관하게 남았다.

```text title="layers.txt"
common  ─┬─ widget   ─┬─ ide
         └─ electron ─┤─ viewer
                      ├─ 업무 앱
                      └─ electron-viewer
```

> [!WARNING]
> Electron 공통 코드는 흡수했다가 다시 분리했다. 폴더 구조만 보면 공통 패키지에 넣는 게 깔끔해 보였지만, 의존성은 폴더가 아니라 `package.json` 단위로 퍼진다. 공통 패키지에 무엇을 넣을지는 그것이 끌고 오는 의존성까지 보고 정해야 한다.

## 계획과 달라진 것

Phase 1B 보고서에는 여섯 단계를 적었다. 3단계에서 업무 앱 전용 코드를 그 앱으로 옮기고, 4단계에서 경유지를 흡수하고, 6단계에서 `shared/`를 없앤다는 순서였다.

실제로는 경유지 폐지와 `shared/` 폐지를 3단계 안에서 했다. 2단계가 끝나자 경유지를 따로 둘 이유가 없었다. 업무 앱 전용으로 분류한 api 클라이언트는 옮기지 않고 공통에 그대로 두었다. 뷰어도 일부를 쓰고 있어서였다.

계획이 바뀐 것은 문제가 아니었다. 소비처 표와 분류가 있었기 때문에 순서를 바꿔도 무엇이 남았는지 확인할 수 있었다.

## 정리

- 옛 IDE를 지우고 이름을 바꾸는 작업은 alias, URI, appId, 설정 폴더 이름까지 문자열 치환으로 한 번에 했다. 기존 타입 오류는 따로 기록해 새 오류와 섞이지 않게 했다.
- 소비처 수를 세어 옮길 것, 둘 것, 지울 것을 나눴다. 이전 순서는 의존 그래프의 바닥부터 잡았다.
- 임시 경유지 패키지와 re-export wrapper를 두고 한 모듈씩 옮겼다. 옮기는 동안 사용처는 바뀌지 않아 빌드가 깨지면 원인이 바로 보였다.
- 모두 옮긴 뒤 import 경로를 한 번에 바꾸고 wrapper를 지웠다. 보호 영역은 확인을 받고 마지막에 바꿨다.
- 경유지와 `shared/`를 없애 공통 패키지를 평평하게 만들고, 위젯과 Electron을 별도 워크스페이스로 뺐다.
- Electron 코드를 공통에 넣었다가 native 의존성이 웹 앱으로 새는 것을 보고 다시 분리했다.
