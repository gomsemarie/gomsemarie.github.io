## 같은 데이터가 두 군데서 무거웠다

팀이 함께 쓰는 사내 변환 도구는 화면 ID 짝표를 운영 데이터에서 받아 온다. As-Is 화면 ID와 To-Be 화면 ID, 프로그램 이름, 진척 같은 칸이 든 엑셀이다. 표 하나가 45만 줄이고, 두 데이터셋을 합치면 약 50만 줄, JSON으로 90MB쯤 된다.

이 데이터가 두 자리에서 무거웠다.

- 데스크톱 쪽: 엑셀을 받아 표로 푸는 자리. 내려받는 파일이 45MB이고, 그 안의 시트 XML을 풀면 수백 MB가 된다.
- 서버 쪽: 푼 표를 들고 찾는 자리. 50만 줄을 전부 JS 객체로 들고 있었고, 검색 한 번이 50만 번의 `includes()`였다.

두 곳 모두 전부를 메모리에 올려 놓고 보고 있었다. 고친 순서는 서버(SQLite 색인)가 먼저, 엑셀 읽기가 나중이지만, 여기서는 데이터가 흐르는 순서대로 적는다.

## 라이브러리 없이 ZIP을 연다

`.xlsx`는 ZIP 안에 XML 몇 개가 든 파일이다. 보통은 엑셀 라이브러리를 쓴다. 쓰지 않은 이유는 반입 심사다. 이 도구는 폐쇄망에 들어가고, 꾸러미가 하나 늘면 그것도 심사를 받아야 한다. 필요한 기능은 ZIP을 풀고 첫 시트의 값을 꺼내는 것 하나였고, ZIP 해제는 `node:zlib`에, 문자열 처리는 Node에 이미 있다.

ZIP은 목차(중앙 디렉터리)가 파일 끝에 있다. 앞에서부터 로컬 헤더를 따라가는 방식은 크기를 데이터 뒤에 적는 항목이 섞여 있으면 믿을 수 없다. 그래서 끝에서부터 목차 끝 표시(EOCD)를 찾는다. ZIP 주석이 최대 65535바이트라 그만큼만 되짚으면 반드시 만난다.

```ts title="zip-entries.ts"
const EOCD = 0x06054b50;

export function findEndOfCentralDir(buf: Buffer): number {
  // 고정 22바이트 + 주석 최대 65535바이트
  const stop = Math.max(0, buf.length - (22 + 0xffff));
  for (let i = buf.length - 22; i >= stop; i--) {
    if (buf.readUInt32LE(i) === EOCD) return i;
  }
  throw new Error('ZIP 파일이 아니다');
}

export function centralDirOf(buf: Buffer) {
  const at = findEndOfCentralDir(buf);
  return {
    count: buf.readUInt16LE(at + 10),
    offset: buf.readUInt32LE(at + 16),
  };
}
```

목차에서 항목 이름, 압축 방식, 크기, 로컬 헤더 위치를 읽고, 압축 방식이 deflate(8)이면 `inflateRawSync`로 푼다. 실제로 걸린 함정이 둘 있었다.

- 로컬 헤더의 이름·확장 길이는 목차에 적힌 값과 다를 수 있다. 데이터 시작점은 반드시 로컬 헤더의 값으로 계산한다.
- 파일이 작아도 쓰는 쪽이 미리 ZIP64로 적는 경우가 있다. 이때 32비트 자리에 `0xFFFFFFFF`가 채워지고 진짜 값은 확장 필드에 들어간다. 이걸 못 읽으면 "ZIP이 아니다"로 떨어져서 무엇이 문제인지 보이지 않는다. 그래서 읽기는 해 둔다.

## XML 파서 없이 줄 단위로 자른다

풀고 나면 시트 XML이 수백 MB짜리 `Buffer`로 남는다. 여기서 `toString()`을 한 번 부르면 그 크기의 문자열이 생기고, DOM 파서로 트리를 쌓으면 그 몇 배가 메모리에 올라간다.

그래서 문자열로 바꾸지 않고 바이트에서 `<row`와 `</row>` 사이만 찾아 한 줄씩 잘라 낸다. 한 번에 문자열로 존재하는 것은 한 줄치뿐이다.

```ts title="row-chunks.ts"
export function* xmlChunks(buf: Buffer, tag: string): Generator<string> {
  const open = Buffer.from(`<${tag}`);
  const close = Buffer.from(`</${tag}>`);
  let pos = 0;
  while (true) {
    const start = buf.indexOf(open, pos);
    if (start < 0) return;
    const gt = buf.indexOf(0x3e, start); // '>'
    if (gt < 0) return;
    if (buf[gt - 1] === 0x2f) {          // <row r="5"/> 같은 빈 줄
      pos = gt + 1;
      continue;
    }
    const end = buf.indexOf(close, gt);
    if (end < 0) return;
    yield buf.toString('utf8', start, end + close.length);
    pos = end + close.length;
  }
}
```

완전한 스트리밍은 아니다. 압축을 푼 시트는 한 덩어리 `Buffer`로 있고, 결과 표도 메모리에 쌓인다. 줄인 것은 거대한 문자열 하나와 그 위의 트리다. 이 정도로 충분했고, 더 나아가면 이 파일이 라이브러리가 되어 버려서 거기서 멈췄다. 수식, 서식, 병합, 여러 시트도 읽지 않는다. 운영 데이터가 내려주는 것은 값만 든 표 한 장이다.

줄 안에서 셀을 꺼낼 때도 엑셀 쪽 사정이 몇 가지 있었다.

- 빈 칸은 아예 적히지 않는다. 셀의 `r` 속성(`AB12`)에서 열 번호를 계산해 빈 자리를 채워야 열이 맞는다. 같은 이유로 칸이 모자란 줄도 버리지 않는다. 버리면 비고가 빈 줄이 전부 사라진다.
- 문자열 셀의 값은 공유 문자열 표의 번호다. 서식이 섞인 글은 조각 여럿으로 쪼개져 오니 이어 붙인다.
- 날짜는 숫자로 들어 있다. 스타일 표에서 그 셀의 서식이 날짜인지 봐야 하고, 이걸 놓치면 날짜 자리에 `46321` 같은 숫자가 오류 없이 들어간다.

> [!WARNING]
> 엑셀 날짜 일련번호의 기준일은 1899-12-30이다. 엑셀이 1900년을 윤년으로 잘못 알아서 있지도 않은 2월 29일이 60번을 차지하기 때문이다. 그래서 60 미만은 하루를 더해야 맞는다. 서식 코드에서 날짜를 판별할 때는 따옴표 안(`"명"`)과 대괄호 안을 건너뛰어야 한다. 안 그러면 `#,##0"명"` 같은 숫자 서식이 `m` 때문에 날짜로 판정된다.

### 진행률과 취소

45만 줄을 푸는 데 1분 남짓 걸린다. 그동안 화면이 멈춘 것처럼 보이면 사람은 껐다 켠다. 그래서 5000줄마다 진행을 알린다. 줄마다 알리면 IPC가 파싱보다 오래 걸린다.

전체 줄 수는 시트 머리의 `<dimension ref="A1:AZ447906"/>`에서 읽는다. 이 값은 선택 항목이고 틀릴 수도 있어서 진행률에만 쓴다. 이 값에 맞춰 읽기를 멈추면 틀린 숫자 하나 때문에 표가 잘린다. 값이 없으면 퍼센트를 지어내지 않고 줄 수만 보여 준다.

취소는 줄 사이에서만 확인하고 예외로 빠져나간다. 반쪽짜리 표가 밖으로 나가지 않게 하려고 그렇게 했다. 취소 예외는 오류 예외와 다른 종류로 둔다. 같은 종류로 두면 취소할 때마다 빨간 오류 상자가 뜬다.

## 50만 번의 includes()를 SQLite로

서버 쪽은 Node에 내장된 `node:sqlite`를 썼다. 네이티브 모듈을 쓰면 플랫폼별 바이너리를 반입물에 같이 넣어야 하고, Node 버전이 바뀌면 다시 빌드해야 한다. 폐쇄망에서는 그때마다 사람이 손을 써야 한다.

표 모양에서 고민한 것은 컬럼을 몇 개로 펼지였다. 운영 데이터 엑셀에는 이름 없는 칸이 많고, 그중 하나를 쓰게 될 때마다 스키마를 고칠 수는 없었다. 그래서 레코드 전체는 JSON 한 칸에 넣고, 찾는 데 쓰는 것만 컬럼으로 뺐다.

```sql title="schema.sql"
CREATE TABLE records (
  dataset  TEXT    NOT NULL,
  asis_id  TEXT    NOT NULL DEFAULT '',
  tobe_id  TEXT    NOT NULL DEFAULT '',
  body     TEXT    NOT NULL,              -- 레코드 전체(JSON)
  haystack TEXT    NOT NULL DEFAULT '',   -- 검색용, 넣을 때 대문자로 접어 둔다
  seq      INTEGER NOT NULL               -- 파일 안에서의 순서
);
CREATE INDEX ix_records_asis ON records(dataset, asis_id);
CREATE INDEX ix_records_seq  ON records(dataset, seq);
```

검색용 칸은 ID 둘과 이름을 이어 붙이고 넣을 때 한 번 대문자로 접는다. 질의할 때마다 `UPPER()`를 50만 번 부르지 않기 위해서다. `LIKE '%q%'`는 앞이 열려 있어 색인을 못 타지만, JS로 도는 것보다 빠르고 50만 개 객체를 만들지도 않는다. `LIMIT`에 걸린 만큼만 JSON을 푼다.

넣기는 한 트랜잭션으로 한다. 자동 커밋으로 넣으면 줄마다 fsync가 돌아서 분 단위로 걸린다. 트랜잭션으로 묶으니 25만 줄에 1.0초였고, 하루 한 번 하는 일이라 이걸로 충분하다. 큰 쓰기에서는 기본값의 fsync가 잦아서 `synchronous = NORMAL`도 주었고, WAL 모드로 열어 팀 전원이 조회하는 동안에도 교체가 돌게 했다.

## 원본은 파일이고 색인은 다시 만든다

사람이 갈아끼우는 것은 JSON 파일이다. SQLite에 든 것은 그 파일을 빨리 찾기 위한 색인이다. 흐름은 파일에서 색인으로 한 방향뿐이라 색인이 깨지면 다시 읽으면 된다. 실제로 기동할 때마다 파일을 통째로 다시 읽어 갈아끼운다. 나중에 화면 ID를 낱개로 가르는 색인 표를 더할 때도 마이그레이션에서 채워 넣지 않았다. 다음 기동이 채운다.

갈아끼우기는 세 단계다. 올려 두는 표에 쌓고(stage), 회귀 표본으로 검증하고, 한 트랜잭션으로 옮긴다(promote). 읽는 사람은 옮기는 순간까지 옛 데이터를 본다. 검증은 올려 둔 쪽 데이터로 돌린다. 살아 있는 쪽으로 돌리면 지금 데이터를 다시 시험하게 되어 늘 통과한다.

시험이 잡아낸 것이 둘 있었다.

- 올려 둔 것 없이 promote하면 `DELETE`만 돌아서 데이터셋이 비었다. 두 번 누르면 데이터가 사라지는 구조였다. 그래서 줄 수 대신 올려 둔 현황 행이 있는지를 보고 판단하게 했다. 파일이 정상적으로 비어 있는 현장도 있기 때문이다.
- stage가 살아 있는 현황 표까지 써서, 다시 읽기가 실패하면 현황이 덮였다. 데이터는 그대로인데 화면에 "0건"이 떴다. 현황 표도 살아 있는 것과 올려 둔 것으로 나눴다.

## ORDER BY 하나가 25만 줄을 훑었다

옮기고 나서 재 보니 변환마다 도는 화면 짝 조회가 느렸다. 원인은 `ORDER BY seq`였다. 이걸 붙이면 SQLite가 정렬을 피하려고 `seq` 색인을 골라 그 데이터셋을 통째로 훑는다. 25만 줄짜리 두 벌로 쟀다.

| 조회 | 전 | 후 |
|---|---|---|
| 화면 짝 조회(5개) | 65.2ms | 0.029ms |
| As-Is ID로 한 건 | 20.1ms | 0.010ms |

필요한 것은 정렬된 결과가 아니라 있으면 하나를 돌려주는 것이었다. `ORDER BY`를 빼면 ID 색인을 탄다. 대신 한 데이터셋 안에 같은 ID가 여럿이면 색인 순서, 곧 넣은 순서로 앞의 것이 정해진다. 이 규칙을 시험으로 고정해 두어서 누가 정렬을 되살리면 시험이 걸린다.

> [!TIP]
> 결과를 통째로 넘기지 않는 것도 효과가 컸다. 짝표는 변환 워커로 구조화 복제되어 넘어가는데, 50만 키를 다 넘기면 변환 한 번마다 447ms가 걸렸다. 원본 화면이 참조하는 ID만 `IN (...)`으로 물어 그만큼만 넘긴다.

## 정리

- `.xlsx`는 ZIP과 XML이다. 첫 시트의 값만 필요하면 `node:zlib`와 `Buffer.indexOf`로 충분했다. 목차는 끝에서부터 읽고, 데이터 위치는 로컬 헤더로 계산한다.
- 시트 XML을 문자열 하나로 만들지 않고 `<row>` 단위로 잘라 한 줄치만 문자열로 둔다.
- 엑셀 날짜는 1900년 윤년 오류와 서식 코드 판별을 챙기지 않으면 숫자로 들어간다.
- 레코드는 JSON 한 칸에 넣고 찾는 데 쓰는 것만 컬럼으로 뺐다. 이름 없는 칸이 많은 데이터여도 스키마를 자주 고치지 않아도 된다.
- 원본은 파일이고 색인은 거기서 만들어 낸다. 깨지면 다시 만든다고 정해 두니 마이그레이션도 단순해졌다.
- 색인을 만들어 놓고도 `ORDER BY` 하나 때문에 엉뚱한 색인을 탈 수 있다. 실측하고, 고친 규칙은 시험으로 고정한다.
