회사 ERP를 새 스택으로 옮기고 있다. 인력, 급여, 계약, 매출·매입을 관리하는 사내 시스템이다. 기존은 Spring Boot + MyBatis API와 별도 웹 화면, 클라우드 VM과 관리형 DB, 오브젝트 스토리지로 돌았다. 새 쪽은 Next.js 한 프로젝트에 화면과 API를 같이 두고, DB는 관리형 PostgreSQL을 쓴다. 폐쇄망에도 그대로 설치할 수 있어야 한다는 조건이 붙었다.

이 시리즈는 그 이관 과정에서 겪은 일을 주제별로 나눠 쓴 것이다. 첫 글은 전체 흐름이다. 저장소 커밋은 10월 7일부터 16일까지 열흘 동안 458개다. 그중 445개는 AI 코딩 에이전트가 작성했다. 나는 그 에이전트를 운영하며 함께 만들었다. 나머지는 동료가 올린 근태·휴가 개편 9개와 자동화 봇 커밋 4개다.

## 원칙: 재현 → 사용성 → 새 기능

저장소 README 맨 위에 순서를 적어 두었다.

1. 기존 기능을 100% 똑같이 재현한다.
2. 그다음 화면과 사용성을 고친다.
3. 마지막에 새 기능을 더한다.

기존 ERP 코드는 전환 때까지 동결했다. 동결한 코드는 "정답"이 된다. 새 API가 맞는지 판단할 기준이 생기는 것이다. 재현을 먼저 둔 이유는 간단하다. 급여나 정산 금액이 기존과 1원이라도 다르면, 그게 개선인지 버그인지 따지는 데만 며칠이 간다. 같다는 것을 먼저 증명하고, 바꾸는 것은 하나씩 결정해서 바꾸기로 했다.

## 첫날: 데이터와 API를 하루에 옮겼다

첫날 커밋은 69개다. 시각 순으로 보면 이렇다.

| 시각 | 한 일 |
|---|---|
| 13:33 | 저장소 시작. 전환 계획 문서, 기존 API 전체 대조표, 이관 스크립트 |
| 13:43 | 기존 DB 덤프 → 새 DB 복원. 테이블별 행 수, 내용 해시, 시퀀스, 함수, 트리거, 인덱스까지 원본과 대조 |
| 13:55 | 첨부 파일 스토리지 이관. 파일마다 크기와 MD5 대조, DB의 파일 경로를 새 위치로 연결 |
| 14:35 | 주민번호 재암호화. 기존 AES/ECB를 복호화해 AES-256-GCM(키 버전 포함)으로 다시 저장 |
| 14:48 | 로그인 계정 생성, 첨부 구조 개편 |
| 15:10 | 기존 MyBatis XML을 그대로 실행하는 해석기 |
| 15:38 | 기존 API 279개 중 270개 이식. 조회 응답 355건 기존과 일치 |
| 16:40 | 쓰기 API 대조. 시나리오 80개 중 70개 일치, 나머지 10개는 의도한 차이 |
| 19:39 | 급여 관련 PDF 표 읽기 이식 |
| 20:18 | 전환 당일 리허설과 절차서 |
| 20:41~ | 화면 이식 시작 |

이식하지 않은 API가 전부 버려진 것은 아니다. 3개는 새 구조로 대체했고(파일 업로드, 상태 확인 등), 4개는 샘플·첫 화면용이라 뺐다. 메신저 발송 기능은 아무도 쓰지 않아서 결정을 받아 범위에서 뺐다.

재암호화를 먼저 한 탓에 생긴 문제도 있었다. 새 DB의 주민번호는 새 형식이라 기존 Java API가 읽지 못한다. 그래서 대조용 기존 API는 새 DB가 아니라, 덤프를 복원한 로컬 DB에 붙여 띄웠다. 이 대조 환경 이야기는 [다음 글](/posts/erp-parity-testing/)에서 따로 다룬다.

10일과 11일은 주말이라 커밋이 없다. 첫날에 이관의 뼈대가 끝났고, 둘째 날부터는 "재현"보다 "사용성" 쪽 일이 많아졌다. 커밋이 가장 많은 날은 9일이다. 이날 커밋은 대부분 화면을 고친 작은 커밋이다. 그리드에서 한글 첫 글자가 사라지는 문제 하나에만 커밋이 여러 개 들어갔다(이 문제는 [따로 정리했다](/posts/glide-grid-korean-ime/)).

13일에는 사내 요청 창구와 에이전트를 이었다. 요청을 확정하면 CI에서 에이전트가 작업 브랜치를 만들고 미리보기 주소를 남긴다. 봇 커밋 4개가 이 경로로 들어온 것이다.

## 사람이 들어간 자리

커밋 작성자만 보면 사람이 한 일이 없어 보인다. 실제로는 몇 군데를 사람이 붙잡고 있었다.

**동작을 바꾸는 결정.** 기존 버그를 고치거나 동작을 바꾸는 항목은 에이전트가 바로 고치지 않고 결정 목록에 올렸다. 사람이 승인한 다음에 반영했다. 대조 문서에는 "사용자 결정 반영"이라는 항목이 따로 있고, 결정마다 대조 기준 수치가 어떻게 바뀌었는지 남아 있다.

**원칙에서 벗어난 개선 되돌리기.** 첫날 18시 39분에 급여 계산을 서버 한 곳으로 모으는 커밋이 들어갔다. 코드로는 더 깔끔했다. 그런데 기존 급여와 보고서 금액이 바뀌는 변경이었다. 2분 뒤 되돌렸고, 알려진 계산 차이는 현행 유지로 문서에 남겼다. "재현 먼저"를 지키려면 이런 개선을 막는 사람이 있어야 했다.

**단계별 병합.** 작업 브랜치에서 개발 통합 브랜치로, 다시 운영 브랜치로 가는 병합은 사람이 확인하고 진행했다. 동료의 근태·휴가 개편도 단계마다 PR로 들어왔다. 14일에는 DB 마이그레이션이 든 PR은 개발 DB에 적용된 것이 확인되기 전에 합치지 못하게 막는 검사를 넣었다.

**운영 DB 마이그레이션.** 운영 DB에 구조 변경을 적용하는 일은 사람이 직접 실행했다. 에이전트에게 주는 안내문에도 "운영 DB 마이그레이션은 사람이 직접 실행한다"를 규칙으로 적었다. 전환 당일 절차서도 단계마다 실행 주체를 적고, 덤프·재암호화처럼 되돌리기 어려운 단계는 사람 또는 사람이 승인한 에이전트로 정했다.

> [!NOTE]
> 에이전트에게 맡긴 것은 "옮기고, 대조하고, 차이를 보고하는 일"이었다. "차이를 받아들일지"는 맡기지 않았다. 이 경계를 정해 두니 속도를 내도 불안하지 않았다.

## 속도를 낸 조건

돌아보면 첫날 속도는 에이전트가 빨라서라기보다 조건이 맞아서 나왔다.

**정답 시스템이 있었다.** 기존 API를 동결해 로컬에 띄우고, 같은 요청을 두 API에 보내 응답과 DB 변화를 비교했다. 에이전트는 "맞게 옮겼다"고 말하는 대신 대조 결과를 내놓았다. 사람은 수백 개 API를 다 읽지 않고 불일치 목록만 보면 됐다.

**SQL을 옮기지 않았다.** 기존 SQL 429개를 손으로 TypeScript로 옮겼다면 하루에 끝날 수 없었다. 매퍼 XML을 그대로 읽어 실행하는 작은 해석기를 먼저 만들었다. 그러자 API 이식은 Java 서비스 코드를 한 줄씩 옮기는 일로 줄었다. 이 해석기는 [3편](/posts/mybatis-xml-interpreter/)에서 다룬다.

**계획을 문서로 먼저 고정했다.** `docs/PLAN.md` 하나에 목표 구조, 결정 사항, 범위에서 뺀 기능, 이관 기록을 모았다. 에이전트는 작업할 때마다 이 문서를 읽고, 작업이 끝나면 기록을 고쳤다.

```md title="PLAN.md (구조만 남긴 예시)"
## 결정 사항
| 항목 | 결정 |
|---|---|
| API | 기존 Java API를 TypeScript로 재작성. SQL은 그대로, 응답은 기존과 1:1 비교 |
| 암호화 | 민감 칸은 AES-256-GCM(키 버전 포함). 기존 데이터는 이관 때 재암호화 |
| 파일 | 비공개 버킷 + 파일 메타 테이블. 다운로드는 권한 확인 뒤 짧은 서명 주소 |

## 범위에서 뺀 기능
- 메신저 발송: 아무도 쓰지 않음. 추후 새로 만든다 (결정일)

## 이관 기록
- (날짜) DB 복원: 행 수 · 내용 해시 · 시퀀스 원본과 일치
- 재실행 순서: dump → restore → storage → reencrypt → accounts → attachments
```

마지막 줄의 재실행 순서가 중요했다. 첫날 한 이관은 1차다. 전환 당일에는 같은 스크립트를 같은 순서로 다시 돌려 운영 데이터를 덮어쓴다. 그래서 모든 이관 스크립트는 다시 돌려도 안전하게 만들었고, 순서는 문서에 고정했다. 주제별 문서(보안, 파일, 권한, 폐쇄망)도 따로 두었다. 폐쇄망 문서에는 "새 라이브러리는 MIT·Apache-2.0·BSD 계열만" 같은 규칙을 적었다. 에이전트가 라이브러리를 고를 때 이 규칙을 따랐다.

## 한계

**정답이 없는 영역은 빠르지 않았다.** 화면은 기존과 똑같이 만드는 것이 목표가 아니었다. 대조할 정답이 없으니 사람이 직접 눌러 보고 고쳐 달라고 해야 했다. 9일의 커밋 124개 대부분이 그렇게 나왔다. 한글 입력, 포커스 테두리, 정렬 버튼처럼 써 봐야 아는 문제들이다.

**자동 점검이 없는 곳은 늦게 알았다.** 매일 백업이 9일부터 실패하고 있었는데 14일에야 고쳤다. 환경변수가 빈 문자열이면 백업 도구가 그 값을 숫자로 읽지 못해 업로드 전에 멈추고 있었다. 운영 로그인 오류도 사용자가 알려 줘서 알았다. 개선 검토 문서의 첫 줄에 "주요 업무 흐름 자동 점검"과 "운영 오류 알림"이 올라간 이유다.

**병렬 작업은 충돌을 남겼다.** 서로 다른 브랜치에서 같은 번호의 마이그레이션을 만들거나, 합치는 과정에서 같은 코드가 두 번 들어간 일이 있었다. 에이전트가 빨리 만들수록 브랜치 사이의 정리는 사람이 챙겨야 했다.

**커밋 수는 성과가 아니다.** 458이라는 숫자에는 한 줄짜리 수정도 많이 들어 있다. 이 숫자는 속도를 보여 줄 뿐, 맞게 만들었다는 근거는 대조 결과 쪽에 있다.

> [!WARNING]
> 정답 시스템이 없는 새 기능에서 같은 속도를 기대하면 안 된다. 이관이 빨랐던 것은 "기존과 같은가"라는 질문이 기계로 답할 수 있는 질문이었기 때문이다.

## 정리

- 순서를 "재현 → 사용성 → 새 기능"으로 정하고, 기존 코드를 동결해 정답으로 썼다.
- 첫날에 DB·파일 이관, 재암호화, API 대부분 이식, 조회·쓰기 대조까지 끝났다. SQL을 옮기지 않고 그대로 실행한 것이 컸다.
- 에이전트에게는 옮기기, 대조, 보고를 맡겼다. 동작을 바꿀지, 병합할지, 운영 DB를 바꿀지는 사람이 정했다.
- 계획과 결정, 재실행 순서를 한 문서에 고정해서 에이전트와 사람이 같은 기준을 봤다.
- 정답이 없는 화면 작업과 자동 점검이 없는 운영 영역은 여전히 사람이 직접 봐야 했다.

다음 글에서는 "기존과 같다"를 어떻게 확인했는지, 대조 테스트를 자세히 다룬다.
