회사 홈페이지를 새로 만들었다. 기존 사이트는 웹 서버, 관리자 서버, API 서버, DB까지 갖춘 구조였지만 실제로 하는 일은 회사 소개와 공지 몇 건을 보여 주는 정도였다. 이것을 Astro 7 정적 사이트로 바꾸고 Vercel에 올렸다.

작업 첫날에만 커밋이 64개 쌓였고, 나흘 뒤 운영 주소로 열었다. 커밋 대부분은 AI 코딩 에이전트가 작성했다. 나는 에이전트에게 작업을 맡기면서 방향을 정하고, 시안을 보고 피드백을 주었다.

여기서는 디자인을 정한 방법을 적는다. 시안을 이미지나 별도 파일로 주고받지 않고, **사이트 안에 시안 전용 페이지를 만들어 실제 데이터로 비교했다.**

## 구조: 정적 사이트와 설계 문서

먼저 큰 틀을 짧게 적는다.

- Astro 정적 출력. adapter 없이 Vercel이 Astro를 자동으로 감지해 배포한다.
- 옛 주소는 `vercel.json`의 `redirects`로 301 처리한다.
- 연혁, 실적, 고객사, 회사 정보는 구조화 데이터(YAML)로, 공지와 뉴스는 Markdown 글로 나눴다.

데이터를 나눈 데는 이유가 있다. 기존 사이트는 연혁과 실적까지 전부 게시글 본문이어서 디자인을 입힐 수가 없었고, 결국 이미지로 만들어 붙여 놓은 상태였다. 데이터로 바꾸니 실적 목록 하나로 홈의 "대표 실적"과 실적 페이지를 함께 만들 수 있었고, 홈의 숫자(업력, 고객사 수, 프로젝트 수)도 데이터에서 계산하게 됐다.

결정은 모두 `docs/DESIGN.md` 한 파일에 적었다. 표 하나에 "항목 / 결정 / 이유"를 쓰고, 결정을 바꾸면 지우지 않고 "1차 제안에서 바꾼 점"에 남겼다. 예를 들어 처음에는 Tailwind를 쓰지 않기로 했다가, 입력 칸이 많은 이력서 폼을 React로 만들게 되면서 Tailwind v4와 shadcn/ui로 바꿨다. 검색 기능(Pagefind)은 넣지 않았다. 공지와 뉴스를 합쳐 7건뿐이라 목록과 연도 필터로 충분했고, "50건을 넘으면 추가한다"는 조건도 같이 적어 두었다.

> [!TIP]
> 에이전트와 일할 때 설계 문서는 지난 일을 남기는 용도보다 다음 작업의 기준으로 더 쓰였다. 다음 세션의 에이전트가 이 파일을 읽고 같은 결정을 이어 간다. 바뀐 결정을 지우지 않고 남겨 두면 같은 논의를 반복하지 않는다.

## 처음 방식: 브랜치로 시안 비교

처음에는 홈 히어로 오른쪽 그림을 정하려고 브랜치를 따로 만들었다. 시안 A~D를 만들고, 반려되면 D1~D4, 다시 E1~E4로 이어 갔다. 확정된 안을 main에 병합하고 나머지는 정리했다.

시안 하나를 정하는 데는 이 방식도 괜찮았다. 하지만 그다음에 정할 것이 홈 문구, 사업 개요, 회사개요, 히어로 배경, 서브페이지 상단까지 다섯 가지였다. 브랜치를 오가며 미리보기 주소를 하나씩 열어서는 비교하기 어려웠다.

## /lab: 사이트 안의 시안 페이지

그래서 사이트 안에 `/lab`이라는 페이지 묶음을 만들었다. 첫 커밋 메시지에 "선택 후 삭제"라고 적어, 처음부터 지울 페이지라는 것을 분명히 해 두었다.

`/lab` 첫 화면은 시안 목록이다.

1. 홈 문구: 영역별 현재 문구와 개선안 4개씩
2. 사업 개요: 본문 디자인 4안
3. 홈 히어로 배경: 4안
4. 회사개요 첫 영역: 내용과 디자인 4안
5. 서브페이지 상단: 4안

시안 페이지는 모두 같은 모양을 따랐다. 위에 비교 목적과 바로가기 버튼을 두고, 그 아래로 "현재 → A → B → C → D"를 세로로 이어 붙였다. 안마다 노란 이름표가 화면 위쪽에 붙어 따라오게 해서, 스크롤하는 중에도 지금 어느 안을 보고 있는지 알 수 있게 했다.

```astro title="OptionLabel.astro (원리만 다시 쓴 예시)"
---
// 시안 비교 전용 이름표. 확정 후 /lab 과 함께 삭제한다.
interface Props { id: string; name: string; desc: string }
const { id, name, desc } = Astro.props;
---
<div id={`opt-${id}`} class="sticky top-16 z-30 border-y border-amber-500 bg-amber-50">
  <div class="container flex flex-wrap items-baseline gap-3 py-3 text-sm">
    <b class="rounded bg-amber-500 px-2">{id}안</b>
    <strong>{name}</strong>
    <span>{desc}</span>
  </div>
</div>
```

시안 페이지가 검색에 걸리면 안 되므로 페이지마다 `noindex`를 넣고 사이트맵에서도 뺐다.

```js title="astro.config.mjs (예시)"
import sitemap from '@astrojs/sitemap';

export default defineConfig({
  integrations: [
    // 시안 페이지는 사이트맵에서 제외한다. 확정 후 이 필터도 함께 지운다.
    sitemap({ filter: (page) => !page.includes('/lab') }),
  ],
});
```

### 실제 데이터와 실제 부품으로 만든다

시안을 사이트 안에 둔 가장 큰 이유는 시안이 실제 데이터와 실제 컴포넌트를 그대로 쓸 수 있어서였다.

홈 문구 시안에서는 문구 안의 업력, 고객사 수, 프로젝트 수가 데이터에서 계산된 값이다. 가짜 숫자를 넣은 시안을 보고 고르면, 실제 숫자가 들어갔을 때 줄이 넘치거나 문장이 어색해질 수 있다. 여기서는 그런 일이 없었다.

히어로 배경 시안도 마찬가지다. 제목, 수치, 실적 티커, 진입 카드는 운영 히어로와 똑같이 두고 배경만 바꿨다. 보는 사람은 배경 차이에만 집중하면 된다.

문구 시안은 사실형, 선언형, 고객 가치형, 간결형의 네 가지 톤으로 나누고, 톤마다 어떤 인상을 주는지 한 줄 설명을 붙였다. 고르는 사람이 문장 하나하나보다 방향을 먼저 고를 수 있게 하려는 것이었다.

## 세 번의 피드백

시안 틀을 만든 커밋부터 확정안을 반영한 커밋까지 한 시간 반쯤 걸렸고, 그사이 피드백이 세 번 오갔다.

**1차.** 문구는 영역마다 2차 수정안을 3개씩 다시 만들고, 추천안에 ★을 달아 그 브랜치의 실제 홈에 먼저 반영했다. 비교는 시안 페이지에서 하고, 추천안이 실제로 어떻게 보이는지는 홈에서 확인했다. 사업 개요는 한 안을 고르지 않고 "B 배치 + A 카드 + D 내용"을 섞은 E안이 나왔다.

히어로 배경에서는 A안의 "포인트" 방식은 좋지만, B안의 시세 라인은 파란색이 하락을 떠올리게 해서 안 되고, C와 D는 빼자는 피드백이 나왔다. 증권 쪽 회사라 색 하나에도 의미가 붙는다는 것을 이때 알았다.

**2차.** A안 계열로 변형 4개를 만들었는데, 돌아온 답은 "오히려 현재가 심플하고 변형들은 난잡하다"였다.

**3차.** 방향을 바꿔 장식을 모두 빼고 배경 톤과 격자만 남긴 단순안 S1~S4를 만들었다. 2차 변형은 비교용으로 아래쪽에 남겼다. 최종으로 고른 것은 S3(사선 톤 한 겹)이다. 기존의 깊이감은 살리고 동그란 번짐만 없앤 안이다.

> [!NOTE]
> 2차에서 "현재가 낫다"는 답이 나올 수 있었던 것은 모든 시안 페이지 맨 위에 "현재"를 늘 같이 띄워 두었기 때문이다. 비교 기준이 없으면 새 안들 중에서만 고르게 된다.

3차 시안을 만들 때 Tailwind에서 한 번 걸렸다. 배경 톤 클래스를 변수로 조립하면 Tailwind가 소스에서 클래스를 찾지 못해 CSS를 만들지 않는다. 그래서 시안 데이터에 클래스 문자열을 통째로 적었다.

```ts title="hero-options.ts (예시)"
// 클래스는 Tailwind 가 소스에서 찾을 수 있도록 문자열 그대로 쓴다.
// `bg-[${color}]` 처럼 조립하면 빌드에 포함되지 않는다.
export const simpleOptions = [
  { id: 'S1', name: '격자만', tone: '[background:var(--color-navy-950)]' },
  { id: 'S3', name: '사선 톤 한 겹',
    tone: '[background:linear-gradient(155deg,rgb(30_58_138/0.38)_0%,transparent_55%),var(--color-navy-950)]' },
];
```

## 확정한 뒤에는 지운다

확정 커밋 하나에 확정안 반영과 `/lab` 삭제를 함께 넣었다. 시안 페이지와 컴포넌트 38개 파일, 사이트맵 필터까지 한 번에 지웠다. 시안 중 계속 쓸 부품(사업 개요의 아이콘)만 일반 컴포넌트 폴더로 옮겼다.

같은 날 서브페이지 상단 그림도 같은 방식으로 정했다. A안을 적용한 뒤 고객사, 소식 페이지 그림을 몇 번 바꿔 보고, 비교 페이지(`/lab/art`)에 띄워 고른 다음 그 페이지도 지웠다.

시안을 바로 지운 이유는 두 가지다.

- 남겨 두면 "나중에 다시 볼 수도 있다"는 이유로 계속 남는다. 시안 컴포넌트 이름이 실제 컴포넌트와 비슷해서 헷갈리기도 한다.
- git 기록에 다 남아 있다. 다시 보고 싶으면 그 커밋으로 돌아가 빌드하면 된다.

하나 더 한 일이 있다. 시안을 확정하면서 새로 쓴 문구를 사실 확인 목록 문서에 따로 적었다. "요건 분석부터 구축·운영까지 함께한다" 같은 문장은 디자인으로는 확정됐지만, 회사가 실제로 그렇게 말할 수 있는지는 담당자가 확인해야 한다. 에이전트가 만든 문장이 확인 없이 공식 문구가 되지 않도록 이 단계를 남겼다.

## 정리

- 회사 홈페이지를 Astro 7 정적 사이트로 다시 만들었다. 첫날 64커밋, 나흘 뒤 운영 오픈이었다. 커밋 대부분은 AI 코딩 에이전트가 썼고 나는 방향과 피드백을 맡았다.
- 결정은 `docs/DESIGN.md` 한 파일에 "결정 / 이유"로 적고, 바뀐 결정도 지우지 않고 남겼다.
- 시안은 사이트 안의 `/lab`에 두었다. 실제 데이터와 실제 컴포넌트를 쓰니 숫자가 들어간 문구나 배경을 실제 모습 그대로 비교할 수 있었다.
- 모든 시안 페이지에 "현재"를 함께 띄웠고, 그래서 "현재가 낫다"는 피드백도 나왔다.
- 시안 페이지는 `noindex`와 사이트맵 제외로 숨겼다가 확정 커밋에서 한꺼번에 지웠다. 필요하면 git 기록에서 다시 볼 수 있다.
- 에이전트가 만든 새 문구는 따로 목록을 만들어 사람이 사실 확인을 하게 했다.
