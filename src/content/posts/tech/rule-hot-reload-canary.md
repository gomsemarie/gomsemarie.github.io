## 서버 하나가 팀 전체의 결과를 바꾼다

변환 룰은 서버 옆 폴더에 원문 그대로 둔다. 폐쇄망 안에서 파일만 넣어 룰을 고칠 수 있게 하려고 그렇게 했다. 그 다음 문제는 고친 룰을 언제, 어떻게 반영하느냐였다.

서버는 팀에 하나다. 룰셋이 바뀌면 그 순간부터 모두의 변환 결과가 바뀐다. 문법이 깨진 룰 하나, 다른 룰의 결과를 건드리는 룰 하나가 곧바로 전원에게 퍼진다. 그래서 룰셋을 갈아 끼우는 방법에 신경을 많이 썼다.

## 파일 감시를 쓰지 않았다

폴더를 watch하다가 파일이 바뀌면 다시 읽는 방법이 먼저 떠오르지만, 일부러 쓰지 않았다.

- 복사가 덜 끝난 상태를 읽을 수 있다. 반쯤 쓰인 `.js`가 올라간다.
- 누가 언제 바꿨는지가 흐려진다. 파일을 넣은 사람과 반영된 시점이 따로 논다.
- 다른 사람이 변환하는 도중에 룰셋이 바뀐다.

대신 파일을 넣은 뒤 설정 화면에서 [다시 읽기]를 누르게 했다. 사람이 의도하고 한 번 누르는 동작이고, 누른 사람이 그 자리에서 결과를 본다.

## 네 단계

[다시 읽기]는 이 순서로 돈다.

1. 새 룰셋을 디스크에서 읽는다. 아직 교체하지 않는다.
2. 격리된 워커에 올려 본다. 문법 오류와 중복 id를 여기서 잡는다.
3. 최근 변환 표본 30건을 새 룰셋으로 돌려 본다. 터지는지, 기존 결과가 바뀌는지 본다.
4. 앞 단계를 다 통과해야 교체한다.

```ts title="reload.ts"
export async function reload({ acceptDrift }: { acceptDrift: boolean }) {
  const next = await ruleFiles.read(); // ① 읽기만 한다

  const probe = await probeLoad(next); // ② 실제로 올려 본다
  if (probe.failures.length > 0) return refuse('올리지 못한 룰이 있습니다', probe);

  const canary = await runCanary(next); // ③ 지난 결과와 견준다
  if (canary.failures.length > 0) return refuse('표본이 터졌습니다', canary);
  if (canary.unstable.length > 0) return refuse('두 번 돌린 결과가 다릅니다', canary);
  if (canary.drifts.length > 0 && !acceptDrift) return refuse('기존 결과가 달라집니다', canary);

  ruleSet.swap(next); // ④ 여기서 처음으로 상태가 바뀐다
  runner.resetIncidents();
  return { applied: true, canary };
}
```

실패하면 아무것도 바뀌지 않는다. 앞의 세 단계는 상태를 건드리지 않고, 교체는 참조 하나를 바꾸는 것으로 끝난다. 반쯤 적용된 룰셋은 어떻게든 피하고 싶었다.

2단계는 꼭 있어야 했다. 처음에는 깨진 룰이 아무 말 없이 빠지고 있었다. 디스크에서 읽는 단계는 파일이 있는지만 보고, 문법 오류는 실행해 봐야 드러난다. 그래서 표본이 하나도 없어도 로드 검사는 항상 돌고, 실패하면 교체를 막는다. 이 기능에서 가장 나쁜 실패는 룰이 소리 없이 사라지는 경우다.

검증은 본 실행기가 아닌 별도 실행기에서 돈다. 본 실행기는 연속 사고 기록을 들고 있어서, 검증하다 난 사고 때문에 멀쩡히 쓰던 룰이 꺼지면 안 된다. 검증용 실행기는 가끔 도는 일이라 예열 워커도 두지 않는다. 표본을 여러 줄로 나눠 돌려 시간을 줄인 내용은 [앞 글](/posts/worker-batching-169ms/)에 적었다.

## 표본은 서버가 모은다

카나리아용 데이터를 사람에게 따로 관리하라고 하면 아무도 관리하지 않는다. 그래서 서버가 직접 모은다. 성공한 변환의 입력, 그때 켜 둔 룰, 그때의 결과를 최근 30건까지 들고 있는다.

```ts title="samples.ts"
export function createSampleStore(limit = 30) {
  const kept = new Map<string, Sample>(); // 삽입 순서 = 오래된 순서

  return {
    add(s: Sample) {
      const k = s.screenId ?? `clip:${s.source.length}:${s.source.slice(0, 64)}`;
      kept.delete(k); // 같은 화면이면 지우고 다시 넣어 최신으로 만든다
      kept.set(k, s);
      while (kept.size > limit) kept.delete(kept.keys().next().value!);
    },
    all: () => [...kept.values()],
  };
}
```

표본은 화면당 하나만 남긴다. 같은 화면을 고쳐서 다시 돌리는 일이 잦아서, 그대로 쌓으면 30건이 전부 같은 화면으로 채워진다. 파싱이 실패했거나 사고가 난 변환은 기준으로 쓸 수 없어서 넣지 않는다.

표본은 그때 켜 둔 룰로 다시 돌린다. 지금 기본값으로 돌리면 비교가 성립하지 않는다. 결과가 달라지면 처음 달라진 줄과 양쪽 내용을 보여 준다. 처음에는 "1줄 → 1줄"처럼 줄 수만 보여 줬는데, 그것만으로는 아무 판단도 할 수 없었다. 의도한 변경이면 [그래도 적용]으로 넘긴다.

표본은 메모리에만 둔다. 디스크에 두면 변환한 소스가 서버에 남는데, 그건 따로 정해야 할 문제다. 그래서 재시작 직후 첫 리로드에는 검증할 표본이 없다. 이때는 통과시키되 응답에 `samples: 0`을 실어서 표본 없이 넘어갔다는 사실을 알린다.

실제로 돌려 봤다. 현장 룰 하나를 넣고 변환해 표본을 만든 뒤, 그 룰을 무력화한 판을 넣고 [다시 읽기]를 눌렀다. 적용이 막히고 "2번째 줄" 차이가 떴다. 그동안 변환은 예전 룰셋으로 돌았다.

## 두 번 돌려도 같아야 한다

나중에 다른 종류의 사고가 났다. 새 화면의 스크립트는 이미 1차 변환된 JS인데, 사람들이 그걸 다시 도구에 넣는 일이 실제로 있었다. 그러면 룰이 두 번 걸린다.

- `x.value`가 `x.value.value`가 됐다.
- 선언이 두 벌 생겼다.
- 함수 본문 주석이 두 번째 변환에서 통째로 사라졌다.

모두 오류 없이 틀린 코드로 나왔다. 400줄짜리 화면에서 `.value.value` 하나를 눈으로 잡아낼 수는 없다.

그래서 모든 룰은 멱등이어야 한다는 규칙을 세웠다. `convert(convert(x)) === convert(x)`다. 카나리아도 표본마다 결과를 두 번 돌려 비교한다. 두 번의 결과가 다르면 [그래도 적용]으로도 넘길 수 없다. 기존 결과가 바뀌는 것(drift)은 의도한 변경일 수 있지만, 두 번 돌려 결과가 달라지는 것은 의도할 수 있는 일이 아니다. 그런 룰은 자기가 만든 결과조차 제대로 읽지 못한다.

## 표본이 모든 룰을 건드리는가

멱등 시험은 룰마다 따로 쓰지 않고 한 곳에 모았다. 반입 룰 전체를 표본에 한 번에 돌린다. 새 룰을 넣는 사람에게 멱등 시험도 같이 써 달라고 부탁하면 언젠가는 빠진다.

그런데 시험이 초록인데도 믿을 수가 없었다. 표본 8개가 실제로 건드리는 룰은 27개 중 7개였다. 나머지 20개는 통과한 게 아니고 아예 돌지 않았는데, 결과는 똑같이 초록이었다.

룰마다 표본을 하나씩 붙여 27개를 모두 덮었다. 그리고 시험을 하나 더 넣었다. 결과에서 실제로 일한 룰을 모아 전체 목록과 비교하고, 한 번도 걸리지 않은 룰이 있으면 이름을 찍으며 실패한다.

```ts title="idempotent.test.ts"
test('모든 룰이 표본에 걸린다', () => {
  const fired = new Set(results.flatMap((r) => r.results.filter((x) => x.changes > 0).map((x) => x.id)));
  const missing = allRuleIds.filter((id) => !fired.has(id));
  assert.deepEqual(missing, [], `표본이 없는 룰: ${missing.join(', ')}`);
});
```

표본 하나를 일부러 지워서 빨간불이 뜨는 것을 확인하고 되살렸다. 표본 이름은 겨냥한 룰 id로 바꿨다. 시험이 터지면 어느 룰을 봐야 하는지 시험 이름으로 바로 알 수 있다.

이 시험에도 구멍이 하나 더 있었다. 룰 목록을 주지 않으면 서버는 기본으로 켜진 룰만 돌린다. 설정에서 룰 하나를 꺼 두면 그 룰은 멱등 확인을 받지 못한다. 그런데 "모든 룰이 표본에 걸린다" 시험은 전체 목록과 비교하므로, 그 룰을 표본이 없다며 실패 처리한다. 설정은 멀쩡한데 빨간불이 떴다. 지금은 시험이 룰을 전부 켜고 돈다. 멱등은 룰 자체의 성질이고, 지금 켜져 있는지와는 관계가 없다.

> [!WARNING]
> 초록불은 "통과했다"와 "확인할 것이 없었다"를 구분하지 않는다. 시험이 대상을 실제로 건드렸는지 따로 세어야 한다.

## 표본에 없는 패턴

카나리아에는 구조적인 한계가 남아 있었다. 이미 쌓인 표본으로만 검사하기 때문에, 새 룰이 표본에 없는 패턴을 건드리면 두 번 돌려 보지도 못하고 통과한다. 멱등이 깨진 룰을 표본에 없는 메서드를 겨냥하게 만들어 넣어 봤더니 그대로 적용됐다.

그래서 룰을 쓰는 화면에서 예시 코드를 넣고 두 번 돌려 볼 수 있게 했다. 서버는 판정 문구를 정하지 않고 사실만 보낸다. 룰 파일이 올라갔는지, 예시 자체가 깨졌는지, 이 파일의 룰이 실제로 일했는지, 두 번 돌린 결과가 같은지다.

룰이 일하지 않았으면 멱등은 자동으로 참이 된다. 확인할 것이 없었을 뿐이다. 그래서 이 경우는 따로 구분해 보내고, 화면도 초록으로 그리지 않는다. 예시는 넣지 않아도 되지만, 없으면 룰 목록에 `표본 없음`으로 남아 빈 곳이 눈에 보인다. 여러 룰의 예시를 한꺼번에 돌릴 때는 앞 글의 배치 통로를 썼다.

> [!NOTE]
> 예시 파일은 룰 폴더에 두지 않고 한 곳의 JSON에 모았다. 룰 옆에 두면 로더가 그것을 공통 파일로 집어 올리고, 예시가 전역을 깔면서 실제 변환에 끼어든다.

## 정리

- 공용 서버의 룰셋 교체는 파일 감시 대신 버튼으로 한다. 반쯤 쓰인 파일을 읽거나 변환 도중에 룰셋이 바뀌는 일을 피한다.
- 읽기, 격리 적재, 표본 재실행, 원자적 교체의 4단계로 돌고, 실패하면 아무것도 바뀌지 않는다.
- 문법 오류는 실행해 봐야 알 수 있어서, 표본이 없어도 로드 검사는 항상 돈다.
- 회귀 표본은 서버가 성공한 변환에서 화면당 하나씩 최근 30건을 모은다. 표본이 비어 있으면 그 사실을 응답에 싣는다.
- 모든 룰은 두 번 돌려도 같은 결과를 내야 한다. 멱등이 깨지면 [그래도 적용]으로도 넘길 수 없다.
- 시험이 초록이어도 대상을 실제로 건드렸는지 센다. 한 번도 걸리지 않은 룰은 이름을 찍으며 실패하게 했다.
