## 룰은 남이 쓴 코드다

[앞 글](/posts/converter-architecture-three-times/)에서 브라우저용 룰 파일을 `node:vm` 컨텍스트에 그대로 올려 서버에서 돌리게 했다. 남은 문제는 그 룰이 서버 하나를 팀 전체가 같이 쓰는 자리에서 돈다는 것이다.

룰은 현장에서 사람이 추가하고 고친다. 언젠가는 `while` 조건을 잘못 써서 끝나지 않는 룰이 들어온다. 같은 스레드에서 무한루프가 돌면 서버가 멈추고, 그 순간 모두의 변환이 멈춘다. 전역을 지저분하게 남기는 룰도 들어온다. 이쪽은 오류 없이 다음 사람의 결과를 조용히 틀리게 만든다.

그래서 룰 실행을 `worker_threads` 워커 안으로 옮기고, 부모 쪽에 실행기를 하나 뒀다. 실행기가 하는 일은 셋이다. 워커 예열, 타임아웃 때 범인 지목, 연속 사고 룰 자동 비활성이다. 이 작업은 AI 코딩 에이전트와 함께 했다.

## 요청당 워커 하나

워커는 변환 한 건을 처리하면 죽는다. 다음 요청은 새 워커가 받는다.

성능만 보면 워커를 재사용하는 쪽이 낫다. 재사용하지 않은 이유는 격리다. 룰은 최상위 `var`와 `window.X`를 쓰는 브라우저 스크립트다. 워커를 재사용하면 앞 요청의 룰이 남긴 전역이 다음 요청에 남는다. 앞 사람이 켠 룰이 깔아 둔 표를 다음 사람의 룰이 읽는 식이다. 오류가 나지 않고 결과만 틀린다. 이런 사고는 찾기 어려워서 성능보다 앞에 뒀다.

vm 컨텍스트만 매번 새로 만들어도 전역은 갈린다. 워커까지 버리는 것은 끊을 수 있어야 해서다. 같은 스레드의 무한루프는 밖에서 멈출 방법이 없다. 워커는 부모가 `terminate()`로 끊을 수 있다. 무한루프 룰을 넣어 시험했을 때 워커는 700ms 만에 끊겼고 부모 프로세스는 살아 있었다.

## 예열: 52ms를 가리는 법

워커를 매번 띄우면 기동 비용이 매번 든다. jscodeshift를 올리는 것까지 쳐서 약 52ms였다. 예열한 뒤 정상 변환 한 건은 30ms 안팎이었다. 변환보다 기동이 더 비쌌다.

그래서 워커를 미리 띄워 둔다. 워커는 준비가 끝나면 `ready`를 보내고 일을 기다린다. 부모는 요청이 오면 데워 둔 워커를 꺼내 쓰고, 꺼내는 즉시 하나를 더 띄운다.

```ts title="warm-pool.ts"
import { Worker } from 'node:worker_threads';

export function createWarmPool(workerPath: string, size = 2) {
  const spares: Promise<Worker>[] = [];

  const spawn = () =>
    new Promise<Worker>((resolve, reject) => {
      const w = new Worker(workerPath, { resourceLimits: { maxOldGenerationSizeMb: 512 } });
      w.once('error', reject);
      w.on('message', function onReady(m: { type: string }) {
        if (m.type !== 'ready') return;
        w.off('message', onReady);
        resolve(w);
      });
    });

  const fill = () => {
    while (spares.length < size) {
      const p = spawn();
      spares.push(p);
      // 예열 실패는 목록에서 빼기만 한다. 다음 take 가 다시 띄운다
      p.catch(() => spares.splice(spares.indexOf(p), 1));
    }
  };

  fill();
  return {
    async take(): Promise<Worker> {
      const next = spares.shift();
      fill(); // 꺼내자마자 채운다
      if (next) {
        try {
          return await next;
        } catch {}
      }
      return spawn();
    },
  };
}
```

하나만 데우면 모자랐다. 변환이 29ms, 예열이 52ms라 연속 요청이 오면 한 번 걸러 한 번은 예열을 기다린다. 둘이면 연속 요청에서도 대기가 사라진다. 그래서 기본값을 2로 잡았다. 공용 서버라 동시 요청도 있다. 대가는 노는 워커 하나만큼의 메모리다.

예열 실패를 `catch`로 삼키는 줄은 빼면 안 된다. 예열 프로미스는 아무도 `await`하지 않은 채 목록에 있으므로, 여기서 던지면 처리되지 않은 거부가 된다.

## 범인 지목

워커가 타임아웃으로 끊기면 무엇이 문제였는지 알아야 한다. "변환이 10초를 넘었습니다"만으로는 아무것도 고칠 수 없다.

워커는 룰을 시작할 때마다 부모에게 `rule-start`를 보낸다. 부모는 마지막으로 받은 룰 id만 기억한다. 타임아웃이 나면 그 룰이 범인이다. 룰은 차례로 돌기 때문에 마지막에 시작하고 끝나지 않은 룰이 멈춘 룰이다.

룰이 수십 개면 메시지도 수십 개다. 메시지 하나가 짧은 문자열이라 구조화 복제 비용은 무시할 만했다. 같은 신호로 그 룰이 도는 동안 찍힌 `console.*`에 룰 id를 붙인다. 로그는 2,000줄에서 자르고, 버린 줄 수를 따로 돌려준다. 조용히 자르면 사람은 마지막 로그를 마지막 일로 읽는다.

범인을 알면 결과를 건질 수 있다. 1차 실패가 나면 그 룰만 빼고 한 번 더 돌린다. 사용자는 결과를 받고 경고를 본다. "도구가 고장났다"보다 "룰 하나가 빠졌다"가 낫다.

```ts title="run-with-retry.ts"
let a = await attempt(build(enabled));

if (!a.ok && a.culprit) {
  incidents.push(strike(a.culprit, a.kind, a.detail));
  // 범인만 빼고 한 번 더. 결과를 아예 못 주는 것보다 낫다
  a = await attempt(build(enabled.filter((id) => id !== a.culprit)));
} else if (!a.ok) {
  // 룰을 시작하기 전에 터졌다. 파싱이나 로딩 단계다
  incidents.push({ ruleId: '(알 수 없음)', kind: a.kind, detail: a.detail, disabled: false });
}
```

여기에는 전제가 하나 있다. 부모가 켠 룰 목록을 알아야 "범인만 뺀 목록"을 만들 수 있다. 목록 없이 "전부 적용"으로 보내면 재시도도, 꺼진 룰 제외도 표현할 수 없다. 서버는 화면에 룰 목록을 보여 주려고 어차피 목록을 들고 있으므로 항상 넘긴다.

## 3진 아웃

재시도로 결과는 받았어도 그 룰은 다음 요청에서 또 멈춘다. 매번 10초를 기다리고 재시도하는 일이 모두에게 반복된다.

그래서 룰마다 연속 사고 횟수를 센다. 같은 룰이 연속 3번 사고를 내면 자동으로 끈다. 꺼진 룰은 처음부터 목록에서 빠진다. 성공적으로 돈 룰은 횟수를 지운다.

룰셋을 다시 읽으면 사고 기록도 지운다. 고친 룰이 들어왔는데 옛 기록 때문에 꺼져 있으면 안 된다.

> [!TIP]
> 룰셋을 검증할 때는 실행기를 따로 만든다. 본 실행기는 사고 기록을 들고 있어서, 검증 중 난 사고로 멀쩡히 쓰던 룰이 꺼질 수 있다.

## vm은 보안 경계가 아니다

여기까지 읽으면 샌드박스처럼 보인다. 아니다. 이걸 코드 첫머리 주석과 커밋에 분명히 적었다.

Node 문서도 `vm`을 보안 장치로 쓰지 말라고 한다. 워커도 같은 프로세스다. 실제로 룰에서 `require('fs')`로 엔진 번들을 읽을 수 있는지 확인해 봤고, 읽혔다. 메모리 상한과 타임아웃은 폭주를 막을 뿐 악의를 막지 못한다.

이 설계가 노리는 것은 둘뿐이다.

1. 룰끼리 전역이 섞이지 않게 한다. 요청마다 새 컨텍스트와 새 워커를 쓴다.
2. 무한루프와 폭주를 부모가 끊게 한다. 워커와 `terminate()`가 맡는다.

이 정도로 충분한 이유는 위협 모델이다. 룰을 쓰는 사람은 같은 회사 사람이다. 엔진은 서버에만 있고 클라이언트로 배포되지 않는다. 막아야 하는 것은 실수이지 공격이 아니다. 외부 사람이 룰을 올릴 수 있게 되면 이 설계로는 부족하다. 그때는 별도 프로세스나 컨테이너로 가야 한다.

> [!WARNING]
> 격리를 보안이라고 적어 두면 나중에 누군가 그 말을 믿고 외부 입력을 받는다. 무엇을 막지 못하는지를 같이 적어야 한다.

## 정리

- 룰은 요청마다 새 워커에서 돈다. 이유는 성능이 아니라 전역 오염 격리다.
- 같은 스레드의 무한루프는 끊을 수 없다. 워커는 `terminate()`로 끊긴다.
- 기동 52ms가 변환 29ms보다 비싸서 워커 둘을 미리 데워 둔다.
- 워커가 룰 시작을 알리므로 타임아웃 때 마지막 시작 룰을 범인으로 지목하고, 그 룰만 빼고 재시도한다.
- 연속 3번 사고를 낸 룰은 자동으로 끄고, 룰셋을 다시 읽으면 기록을 지운다.
- vm과 워커는 보안 경계가 아니다. 막는 것은 실수이고, 그 전제를 코드에 적어 둔다.
