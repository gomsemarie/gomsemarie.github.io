## 룰은 남이 쓴 코드다

[앞 글](/posts/converter-architecture-three-times/)에서 브라우저용 룰 파일을 `node:vm` 컨텍스트에 그대로 올려 서버에서 돌리게 했다. 남은 문제는 그 룰이 팀 전체가 같이 쓰는 서버 하나에서 돈다는 점이었다.

룰은 현장에서 사람이 추가하고 고친다. 언젠가는 `while` 조건을 잘못 써서 끝나지 않는 룰이 들어올 것이다. 같은 스레드에서 무한루프가 돌면 서버가 멈추고, 그 순간 모두의 변환이 멈춘다. 전역을 지저분하게 남기는 룰도 들어온다. 이런 룰은 오류 없이 다음 사람의 결과를 조용히 틀리게 만든다.

그래서 룰 실행을 `worker_threads` 워커 안으로 옮기고 부모 쪽에 실행기를 하나 뒀다. 실행기는 워커를 미리 띄워 두고, 타임아웃이 나면 어느 룰이 멈췄는지 짚고, 사고를 연달아 내는 룰을 자동으로 끈다.

## 요청당 워커 하나

워커는 변환 한 건을 처리하면 죽고, 다음 요청은 새 워커가 받는다.

성능만 보면 워커를 재사용하는 편이 낫다. 그래도 재사용하지 않은 이유는 격리다. 룰은 최상위 `var`와 `window.X`를 쓰는 브라우저 스크립트라서, 워커를 재사용하면 앞 요청의 룰이 남긴 전역이 다음 요청까지 남는다. 앞 사람이 켠 룰이 깔아 둔 표를 다음 사람의 룰이 읽는 식이다. 이때 오류는 나지 않고 결과만 틀린다. 찾기 어려운 사고라서 성능보다 먼저 막기로 했다.

전역만 가르려면 vm 컨텍스트를 매번 새로 만드는 것으로도 된다. 워커까지 버리는 이유는 실행을 끊을 수 있어야 해서다. 같은 스레드에서 도는 무한루프는 밖에서 멈출 방법이 없지만, 워커는 부모가 `terminate()`로 끊을 수 있다. 무한루프 룰을 넣어 시험했더니 워커는 700ms 만에 끊겼고 부모 프로세스는 살아 있었다.

## 예열로 기동 52ms를 감춘다

워커를 매번 띄우면 기동 비용도 매번 든다. jscodeshift를 올리는 시간까지 쳐서 약 52ms였다. 예열한 뒤 정상 변환 한 건은 30ms 안팎이었으니, 변환보다 기동이 더 비쌌다.

그래서 워커를 미리 띄워 둔다. 워커는 준비가 끝나면 `ready`를 보내고 일을 기다린다. 부모는 요청이 오면 미리 띄워 둔 워커를 꺼내 쓰고, 꺼내자마자 하나를 더 띄운다.

```ts title="warm-pool.ts"
import { Worker } from 'node:worker_threads';

export function createWarmPool(workerPath: string, size = 2) {
  const spares: Promise<Worker>[] = [];

  const spawn = () =>
    new Promise<Worker>((resolve, reject) => {
      const w = new Worker(workerPath, { resourceLimits: { maxOldGenerationSizeMb: 512 } });
      w.once('error', reject);
      w.on('message', function onReady(m: { type: string }) {
        if (m.type !== 'ready') return;
        w.off('message', onReady);
        resolve(w);
      });
    });

  const fill = () => {
    while (spares.length < size) {
      const p = spawn();
      spares.push(p);
      // 예열 실패는 목록에서 빼기만 한다. 다음 take 가 다시 띄운다
      p.catch(() => spares.splice(spares.indexOf(p), 1));
    }
  };

  fill();
  return {
    async take(): Promise<Worker> {
      const next = spares.shift();
      fill(); // 꺼내자마자 채운다
      if (next) {
        try {
          return await next;
        } catch {}
      }
      return spawn();
    },
  };
}
```

하나만 띄워 두면 모자랐다. 변환이 29ms, 예열이 52ms라서 요청이 연달아 오면 두 번에 한 번은 예열을 기다리게 된다. 둘을 띄워 두면 연속 요청에서도 기다림이 없어서 기본값을 2로 잡았다. 공용 서버라 동시 요청도 있다. 대신 놀고 있는 워커 하나만큼 메모리를 더 쓴다.

예열 실패를 `catch`로 삼키는 줄은 빼면 안 된다. 예열 프로미스는 아무도 `await`하지 않은 채 목록에 들어 있으므로, 여기서 던지면 처리되지 않은 거부가 된다.

## 멈춘 룰 찾기

워커가 타임아웃으로 끊기면 무엇이 문제였는지 알아야 한다. "변환이 10초를 넘었습니다"라는 말만으로는 아무것도 고칠 수 없다.

워커는 룰을 시작할 때마다 부모에게 `rule-start`를 보내고, 부모는 마지막으로 받은 룰 id만 기억한다. 룰은 차례로 돌기 때문에, 타임아웃이 났을 때 마지막으로 시작하고 끝나지 않은 룰이 멈춘 룰이다.

룰이 수십 개면 메시지도 수십 개가 오간다. 메시지 하나가 짧은 문자열이라 구조화 복제 비용은 무시할 만했다. 같은 신호를 써서 그 룰이 도는 동안 찍힌 `console.*`에 룰 id를 붙인다. 로그는 2,000줄에서 자르고, 버린 줄 수를 따로 돌려준다. 말없이 자르면 사람은 남은 마지막 로그를 마지막으로 일어난 일로 읽는다.

멈춘 룰을 알면 결과도 건질 수 있다. 첫 시도가 실패하면 그 룰만 빼고 한 번 더 돌린다. 사용자는 결과를 받고 경고를 함께 본다. 도구가 고장 났다는 말보다 룰 하나가 빠졌다는 말이 낫다.

```ts title="run-with-retry.ts"
let a = await attempt(build(enabled));

if (!a.ok && a.culprit) {
  incidents.push(strike(a.culprit, a.kind, a.detail));
  // 범인만 빼고 한 번 더. 결과를 아예 못 주는 것보다 낫다
  a = await attempt(build(enabled.filter((id) => id !== a.culprit)));
} else if (!a.ok) {
  // 룰을 시작하기 전에 터졌다. 파싱이나 로딩 단계다
  incidents.push({ ruleId: '(알 수 없음)', kind: a.kind, detail: a.detail, disabled: false });
}
```

이렇게 하려면 부모가 켠 룰 목록을 알고 있어야 한다. 그래야 그 룰만 뺀 목록을 만들 수 있다. 목록 없이 "전부 적용"으로 보내면 재시도도, 꺼 둔 룰 제외도 표현할 방법이 없다. 서버는 화면에 룰 목록을 보여 주려고 어차피 목록을 들고 있으므로 늘 넘긴다.

## 연속 3번 사고 나면 끈다

재시도로 결과는 받아도, 그 룰은 다음 요청에서 또 멈춘다. 그러면 모두가 매번 10초를 기다리고 재시도를 겪는다.

그래서 룰마다 연속 사고 횟수를 센다. 같은 룰이 연속 3번 사고를 내면 자동으로 끄고, 꺼진 룰은 처음부터 목록에서 빠진다. 문제없이 돈 룰은 횟수를 지운다.

룰셋을 다시 읽을 때도 사고 기록을 지운다. 고친 룰이 들어왔는데 옛 기록 때문에 꺼져 있으면 안 된다.

> [!TIP]
> 룰셋을 검증할 때는 실행기를 따로 만든다. 본 실행기는 사고 기록을 들고 있어서, 검증하다 난 사고 때문에 멀쩡히 쓰던 룰이 꺼질 수 있다.

## vm은 보안 경계가 아니다

여기까지만 보면 샌드박스 같지만 그렇지 않다. 이 점은 코드 첫머리 주석과 커밋 메시지에 분명히 적었다.

Node 문서도 `vm`을 보안 장치로 쓰지 말라고 한다. 워커도 같은 프로세스 안에서 돈다. 실제로 룰에서 `require('fs')`로 엔진 번들을 읽을 수 있는지 확인해 봤더니 읽혔다. 메모리 상한과 타임아웃은 폭주를 막을 뿐이고 악의는 막지 못한다.

이 설계가 노리는 것은 두 가지다.

1. 룰끼리 전역이 섞이지 않게 한다. 요청마다 새 컨텍스트와 새 워커를 쓴다.
2. 무한루프와 폭주를 부모가 끊을 수 있게 한다. 워커와 `terminate()`가 맡는다.

이 정도면 되는 이유는 위협 모델에 있다. 룰을 쓰는 사람은 같은 회사 사람이고, 엔진은 서버에만 있고 클라이언트로 배포되지 않는다. 막아야 하는 것은 실수이고 공격은 아니다. 외부 사람이 룰을 올릴 수 있게 되면 이 설계로는 부족하고, 그때는 별도 프로세스나 컨테이너로 옮겨야 한다.

> [!WARNING]
> 격리를 보안이라고 적어 두면 나중에 누군가 그 말을 믿고 외부 입력을 받는다. 무엇을 막지 못하는지도 같이 적어 둬야 한다.

## 정리

- 룰은 요청마다 새 워커에서 돈다. 성능 때문이 아니고 전역 오염을 막기 위해서다.
- 같은 스레드의 무한루프는 끊을 수 없지만 워커는 `terminate()`로 끊긴다.
- 기동 52ms가 변환 29ms보다 비싸서 워커 둘을 미리 띄워 둔다.
- 워커가 룰 시작을 알려 주므로, 타임아웃이 나면 마지막으로 시작한 룰을 범인으로 보고 그 룰만 빼고 재시도한다.
- 연속 3번 사고를 낸 룰은 자동으로 끄고, 룰셋을 다시 읽으면 기록을 지운다.
- vm과 워커는 보안 경계가 아니다. 막는 대상은 실수이며, 그 전제를 코드에 적어 뒀다.
