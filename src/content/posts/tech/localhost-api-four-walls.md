## 무엇을 붙이려 했나

사내 변환 도구를 쓰는 사람들 중에는 반복 작업을 매크로로 돌리는 사람이 있다. 그 매크로 프로그램은 웹뷰 기반 데스크톱 앱이고, 사람이 JS로 스크립트를 짜서 돌린다. 요청은 간단했다. 매크로에서 변환 도구의 조회·변환·검증을 부르고 싶다는 것이다.

먼저 정한 것은 창구를 어디에 열지였다. 변환 도구는 팀에 하나인 서버(`apps/api`)와 사람마다 띄우는 Electron 클라이언트로 되어 있다. 서버에 열면 안 됐다.

- 서버는 팀에 하나다. 매크로는 사람마다 자기 PC에서 돈다. 팀 서버에 창구를 열면 남의 매크로가 내 작업을 부를 수 있다.
- 서버에는 "바깥으로 나가는 `fetch`가 없다"는 설계 경계가 있었다.

그래서 각자의 Electron 메인 프로세스에 WebSocket 창구를 열고, 말은 JSON-RPC 2.0의 부분집합으로 정했다. 받은 부름은 렌더러로 넘긴다. 룰·캐시·세션 갱신이 다 창 안에 있어서, 메인 프로세스가 API를 직접 부르면 같은 로직이 두 벌이 되기 때문이다. 이 작업은 AI 코딩 에이전트와 함께 작업했다.

## 누가 127.0.0.1에 닿는가

"로컬에서만 여는 포트니까 괜찮다"는 말을 먼저 의심했다. 이 포트에 닿을 수 있는 상대를 셋으로 나눠 보았다.

1. 사내망의 다른 PC
2. 이 PC의 브라우저에 열린 아무 웹페이지
3. 이 PC에서 도는 다른 프로그램

1번은 바인딩 주소로 막힌다. 2번이 의외로 넓다. 브라우저의 `fetch`는 CORS가 막아 주지만 WebSocket에는 CORS가 없다. 사람이 열어 둔 아무 탭의 스크립트가 `ws://127.0.0.1:<포트>`로 그냥 붙는다. 3번은 1·2번 벽을 그대로 지나간다. 같은 PC의 프로그램은 루프백 주소로 붙을 수 있고, 브라우저가 아니니 `Origin`을 안 붙이면 그만이다.

그래서 벽을 넷으로 두었다. 어느 하나도 혼자서는 충분하지 않다.

| 벽 | 막는 것 |
|---|---|
| `127.0.0.1` 고정 | 사내망의 다른 PC |
| `Origin`이 있으면 거절 | 브라우저의 웹페이지 |
| 비밀 파일과 증표 | 이 PC의 아무 프로그램 |
| 메서드 허용 목록 | 붙은 뒤에 할 수 있는 일의 범위 |

## 첫 번째 벽: 127.0.0.1 고정

`listen(port, '127.0.0.1')`로 연다. 바인딩 주소를 설정 항목으로 만들지 않았다. 설정으로 열어 두면 언젠가 누가 `0.0.0.0`을 적는다. 포트만 화면에서 고칠 수 있다.

평범한 HTTP 요청에는 본문 없는 404만 돌려준다. 무엇이 도는 창구인지 말해 주면 포트를 훑는 쪽에 "여기 그 도구가 있다"를 알려 주는 셈이다.

## 두 번째 벽: Origin이 있으면 거절

브라우저는 WebSocket 손잡기에 `Origin` 헤더를 반드시 붙이고, 페이지 스크립트는 그것을 지울 수 없다. 이 성질을 이용해 손잡기 단계에서 `Origin`이 있으면 403으로 돌려보낸다.

```ts title="origin-guard.ts"
export function isOriginAllowed(origin: string | undefined, allowList: readonly string[]): boolean {
  // 브라우저가 아닌 클라이언트는 Origin을 안 붙인다
  if (origin === undefined || origin === '' || origin === 'null') return true;
  // 사람이 손으로 넣은 값만, 글자 전체가 같을 때만
  return allowList.includes(origin);
}
```

실제로 붙여 보니 이 벽에 정상 프로그램이 먼저 걸렸다. 매크로 프로그램의 웹뷰(WebView2)가 손잡기에 `Origin`을 붙여 보냈다. 그래서 허용 목록을 두되 규칙을 좁혔다.

- 막힌 `Origin` 값을 설정 화면에 그대로 띄우고, 사람이 읽고 [열어 주기]를 누르게 했다. 자동으로 열지 않는다.
- 프로그램이 스스로 자기를 목록에 올리는 길은 없다. 붙으려는 쪽이 자기를 올릴 수 있으면 이 벽은 없는 것과 같다.
- 앞자리 맞추기와 와일드카드를 받지 않는다. 글자 전체가 같아야 한다. 접두어로 비교하면 `https://a.com`이 `https://a.com.attacker.net`을 통과시키는 식의 빈틈이 생기고, 그 빈틈은 아무 표시도 안 난다.

허용하는 순간 벽 하나가 낮아진다는 점은 화면에 늘 보이게 했다. 그 출처의 웹페이지는 이제 붙을 수 있다. 다만 다음 벽이 남아 있다.

## 세 번째 벽: 비밀 파일과 증표

같은 PC의 프로그램을 가르는 것은 "이 비밀을 아는가"다. 비밀을 어떻게 전달하느냐가 문제였다.

처음 떠올린 것은 사람이 값을 복사해 매크로의 전역 스크립트에 붙여 넣는 방식이다. 그러면 그 비밀이 매크로를 짜는 모든 사람에게 평문으로 보이고, 공유되는 스크립트에 남는다. 그래서 창구를 열 때 사용자 데이터 폴더에 비밀 파일을 쓰고, 외부 프로그램이 그 파일을 직접 읽게 했다. 파일에는 실제로 잡힌 포트와 비밀이 들어 있다. 포트 `0`을 주면 운영체제가 빈 포트를 고르는데, 설정값을 그대로 적으면 파일에 `0`이 적혀 영영 못 붙는다.

비밀은 켤 때마다 새로 만들고, 창구를 닫을 때 파일을 지운다. 옛 비밀이 남아 있으면 껐다 켰는데도 아까 붙어 있던 쪽이 계속 유효하다.

비밀 자체는 선으로 보내지 않는다. 서버가 연결마다 새 nonce를 던지고, 클라이언트가 비밀을 열쇠로 nonce에 HMAC-SHA256을 계산해 답한다. 선을 엿봐도 비밀은 지나가지 않고, 같은 답을 다시 쓸 수도 없다.

```ts title="challenge.ts"
import { createHmac, randomBytes, timingSafeEqual } from 'node:crypto';

export const newChallenge = (): string => randomBytes(32).toString('hex');

export function answerFor(secret: string, challenge: string): string {
  return createHmac('sha256', secret).update(challenge).digest('hex');
}

export function verifyAnswer(secret: string, challenge: string, given: unknown): boolean {
  if (typeof given !== 'string') return false;
  const want = Buffer.from(answerFor(secret, challenge));
  const got = Buffer.from(given);
  if (want.length !== got.length) return false; // timingSafeEqual은 길이가 다르면 던진다
  return timingSafeEqual(want, got);
}
```

`===`로 비교하지 않는 이유는 시간 차다. 문자열 비교는 다른 글자를 만나는 순간 끝나서, 걸린 시간이 몇 글자까지 맞았는지를 알려 준다.

연결 쪽 규칙도 몇 가지 더했다.

- 인증 전에는 인증 답 하나만 받는다. 다른 부름에는 "먼저 인증해야 한다"만 돌려준다.
- 증표가 틀리면 그 자리에서 끊는다. 같은 연결에서 다시 넣어 보게 두면 그게 곧 무차별 대입이다.
- 5초 안에 인증하지 않는 연결은 치운다. 붙는 것 자체는 누구나 되니, 아무 말 없이 자리만 차지하는 연결을 정리해야 한다.
- 규약 판 번호를 증표보다 먼저 본다. 판이 안 맞는데 "증표 불일치"로 답하면 상대는 엉뚱하게 비밀을 의심한다.

> [!WARNING]
> 이 벽의 한계도 적어 둔다. 파일 권한을 `0o600`으로 좁히지만 Windows에서 `chmod`는 읽기 전용 표시만 바꾸고 ACL은 건드리지 않는다. Windows에서 이 파일을 지키는 것은 사용자 프로필 아래 폴더에 있다는 사실이다. 같은 사용자 권한으로 도는 프로그램이 마음먹고 그 파일을 읽는 것까지 막는 장치는 아니다. 내가 이 벽에 기대하는 것은 "이 PC의 아무 프로그램이나 비밀 없이 붙는 것"을 막는 데까지다.

## 네 번째 벽: 메서드 허용 목록

붙은 뒤에 부를 수 있는 것을 목록으로 정했다. 이름 규칙으로 막지 않는다. "특정 접두어로 시작하면 다 된다"는 식이면 나중에 누가 그 접두어로 새 기능을 열고, 그 사실이 아무 데도 안 남는다. 메인 프로세스의 배열 하나에 한 줄을 더해야만 열린다. 무엇이 밖으로 열려 있는지를 그 배열 하나로 다 읽을 수 있다.

처음 연 것은 열 가지다. 조회·변환·검증 같은 기능 부름과, 탭 이동·검색·칸 채우기 같은 화면 제어다. 칸 채우기는 그 칸을 가진 화면이 자기를 등록하게 했다. 창구가 DOM을 뒤지면 화면이 바뀔 때마다 조용히 깨진다. 일부러 안 연 것도 있다.

- 코드를 받아 실행하는 메서드. `eval` 류가 하나라도 있으면 앞의 세 벽이 통째로 뜻을 잃는다.
- 실제 화면 정의를 고치는 되쓰기. 매크로가 200개를 고쳐 놓고 아무도 모르는 일이 생기면 되돌릴 길이 형상관리뿐이다. 사람이 화면에서 누른다.

무엇을 부를 수 있는지 묻는 메서드도 인증 뒤에만 답한다. 창구가 무엇을 할 수 있는지가 곧 공격 면이다. 목록에 없는 이름을 부른 기록은 남긴다. "왜 안 되지"의 절반이 이름 오타였다.

## 알림도 같은 통로로

나중에 반대 방향도 열었다. 변환이 끝나거나 화면을 올리면 붙어 있는 외부 프로그램이 먼저 알게 하는 것이다. 처음에는 SSE를 하나 더 낼 뻔했는데, JSON-RPC에서 `id` 없는 메시지가 곧 알림이라 새 통로가 필요 없었다. 알림은 인증한 연결에만 보낸다. 인증을 기다리는 연결에 흘리면 비밀 파일을 못 읽은 쪽이 무슨 일이 벌어지는지 지켜볼 수 있다. 알림에는 일어난 일의 종류만 싣고 값은 싣지 않는다. 필요하면 상대가 기존 메서드로 다시 묻는다.

> [!NOTE]
> 실물에 처음 붙인 날, 손잡기 응답에 쓰는 RFC 6455 고정 GUID가 한 자리 밀려 있어 규약을 지키는 클라이언트가 조용히 끊던 일도 드러났다. 이 이야기는 의존성을 직접 짠 기록에서 따로 다룬다.

## 정리

- WebSocket에는 CORS가 없다. 루프백에 연 포트는 브라우저의 아무 탭에서도 닿는다.
- 같은 PC의 프로그램은 `127.0.0.1` 바인딩과 `Origin` 검사를 그냥 지나간다. "로컬이라 안전하다"가 틀리는 지점이 여기다.
- 비밀은 사람이 복사해 붙이지 않고 파일로 읽게 한다. 켤 때마다 새로 만들고, 닫을 때 지운다. 선으로는 nonce에 대한 HMAC만 보낸다.
- 허용 목록은 글자 전체 일치, 사람이 손으로 넣은 값만 받는다. 프로그램이 자기를 올릴 수 있으면 벽이 아니다.
- 부를 수 있는 것은 이름 규칙이 아니라 목록으로 정하고, 코드 실행과 되돌리기 어려운 쓰기는 열지 않는다.
- 벽마다 무엇을 막고 무엇을 못 막는지 적어 둔다. 한계를 모르는 벽은 과신하게 된다.
