회사에서 노코드 UI 빌더를 만들고 있다. 업무 화면을 코드 대신 끌어다 놓기로 조립하는 도구다. 지금 모양이 나오기까지 세 번을 갈아엎었다. 처음에는 오픈소스 라이브러리를 붙여 봤고, 그다음에는 직접 하나를 만들었고, 그것도 버리고 코어부터 다시 만들었다. 시리즈 첫 글로 각 단계에서 무엇을 보고 다음으로 넘어갔는지 적어 둔다.

## 빌더가 하는 일

빌더는 사내 IDE 안의 탭 하나로 열린다. 화면은 네 부분으로 나뉜다.

- **캔버스**: 위젯을 끌어 옮기고, 8방향으로 크기를 바꾸고, 빈 곳을 끌어 여러 개를 고른다.
- **팔레트**: 버튼, 입력, 달력, 그리드 같은 위젯 목록이다. 캔버스로 끌어다 놓으면 추가된다.
- **아웃라이너**: 위젯 트리를 보여 준다. 여기서도 순서를 바꾸거나 부모를 옮길 수 있다.
- **인스펙터**: 고른 위젯의 속성을 편집한다. 여러 개를 고르면 공통 속성만 보여 준다.

결과물은 JSON 파일 하나다. 위젯 트리, 속성, 이벤트 스크립트, 데이터셋 정의가 들어 있다. 실제 화면을 띄우는 뷰어는 이 JSON을 TSX로 바꿔 쓴다. 편집기에서 보이는 위젯과 뷰어에서 돌아가는 위젯은 같은 React 컴포넌트다. 같은 컴포넌트가 편집기와 뷰어 양쪽에서 돌아야 한다는 이 조건이 뒤에서 계속 걸림돌이 됐다.

## 첫 번째: puck을 붙여 봤다

2025년 8월 18일, 오픈소스 빌더인 puck을 의존성에 넣고 IDE 화면에 붙였다. 샘플 화면 JSON도 하나 만들었다. 직접 만들기 전에 이미 있는 것으로 어디까지 갈 수 있는지 보고 싶었다.

그 뒤 열흘 남짓 동료들이 이어서 붙였다. 기본 세팅, flex 레이아웃이 보이게 하는 수정, 버튼 스타일, 속성 편집, 저장까지 들어갔다. 그런데 8월 26일에 나는 자체 빌더의 첫 커밋을 "미완"이라는 메시지로 올렸다. puck 작업은 8월 29일 저장 기능 커밋을 마지막으로 멈췄다.

puck을 접은 이유를 적어 둔 문서는 남아 있지 않다. 지금 정리된 요구사항과 견주어 보면 어디서 맞지 않았는지는 짐작이 간다.

- 위젯은 편집기와 뷰어에서 같은 코드로 돌아야 했다. 뷰어의 스크립트는 `setValue` 같은 위젯 메서드를 부른다. 메서드는 JSON에 저장할 수 없으니 저장 모델 밖에 둬야 한다.
- 드래그와 리사이즈는 위치를 매 프레임 바꾼다. React 렌더를 거치지 않고 DOM을 직접 고쳐야 60fps가 나온다.
- 위젯을 좌표로 배치하는 방식이 필요했다. 블록을 흐름에 끼워 넣는 방식과는 출발점부터 다르다.

라이브러리는 자기 데이터 모델과 렌더 경로를 갖고 있다. 위 요구는 모두 그 안쪽을 고쳐야 들어줄 수 있었다.

## 두 번째: 직접 만든 첫 빌더

첫 자체 빌더는 2025년 8월 말부터 11월까지 만들었다. 트리, 형제 사이에 끼워 넣는 드롭존, 선택한 요소를 따라다니는 액션바, 스크립트 편집, 저장 시 변경 여부 표시가 이 시기에 들어갔다. 9월 초부터는 react-scan을 붙여 리렌더를 보면서 상태 관리를 몇 차례 고쳤다.

### WeakRef로 만든 요소 캐시

요소는 중첩 트리로 저장했다. 어떤 요소를 id로 찾으려면 트리를 내려가야 했다. 그래서 id로 요소와 경로를 찾는 캐시를 모듈에 두었다. 요소 참조는 `WeakRef`로 잡았다. 트리에서 빠진 요소는 GC가 치우게 하려는 생각이었다.

```ts title="element-cache.ts"
type Path = number[];
interface Entry<T> { ref: WeakRef<T>; path: Path }

class TreeCache<T extends { id: string; children?: T[] }> {
  private map = new Map<string, Entry<T>>();

  get(id: string, root: T): T | null {
    const hit = this.map.get(id)?.ref.deref();
    if (hit) return hit;
    const found = findWithPath(root, id); // 캐시 미스면 트리를 내려간다
    if (!found) return null;
    this.map.set(id, { ref: new WeakRef(found.node), path: found.path });
    return found.node;
  }

  invalidate(ids?: string[]) {
    ids ? ids.forEach((id) => this.map.delete(id)) : this.map.clear();
  }
}
```

이 캐시는 오래 쓰지 못했다. 9월 23일 하루 동안 캐시 hook을 추가하고, 캐시 문제를 고치고, 마지막에는 캐시를 store 안의 `Map`으로 옮겼다. 고친 커밋에는 "추후 캐시 개선 필요"라고 남겼다.

지금 보면 상태를 immer로 바꾸는 구조와 맞지 않았다. immer는 바뀐 경로의 객체를 새로 만든다. 모듈 캐시가 잡고 있던 옛 객체는 GC 전까지 살아 있으니 `deref()`가 성공한다. 오래된 값을 돌려줘도 캐시 쪽에서는 알 길이 없었다. 무효화를 하나도 빠뜨리지 않는 수밖에 없었다.

> [!NOTE]
> `WeakRef`는 메모리 회수를 돕는 도구다. 최신 값을 보장해 주지는 않는다. 불변 갱신을 쓰는 상태라면 캐시를 상태와 같은 곳에 두고 함께 갱신하는 편이 안전하다.

### absolute 좌표계 실험

11월 13일에는 "absolute 좌표계 임시 커밋"을 올렸다. 위젯마다 `position {x, y}`와 `dimensions {width, height}`를 갖는 transform 속성 그룹을 만들고, 왼쪽·가운데·오른쪽 정렬 버튼이 부모 너비를 읽어 x를 계산하게 했다.

흐름 레이아웃을 좌표 레이아웃으로 바꾸는 일은 속성 몇 개 더하는 것으로 끝나지 않았다. 드래그는 어디에 끼울지를 정하던 동작에서 어느 좌표로 옮길지를 정하는 동작으로 바뀐다. 자식 좌표가 어느 부모를 기준으로 하는지도 정해야 한다. 두 달 반 뒤 새 빌더는 상태 모델부터 다시 시작했다.

## 세 번째: 코어부터 다시

2026년 2월 2일에 새 빌더 기능 폴더를 만들었다. 이번에는 위젯을 그리기 전에 코어를 먼저 잡았다. 화면 구조(schema)와 원본 파일(source) 기본 구조는 동료와 나눠 만들었다.

- **정규화 모델**: 트리 대신 `Record<id, Node>`로 저장한다. 노드는 부모 id와 자식 id 목록을 가진다. 아무 노드나 한 번에 찾고 고칠 수 있다.
- **undo/redo**: 쓰기 액션을 고차 함수로 감싸 immer patch를 기록한다. 액션 하나가 히스토리 하나다.
- **store 병합**: 설정과 schema를 나눠 뒀다가 2월 16일 하나의 코어 store로 합쳤다.
- **드래그**: 끌기 시작하면 원본 요소를 `fixed`로 띄우고 viewport 기준으로 움직인다. 2월 20일에는 스냅 모듈이 들어갔다. 스냅 엔진은 [별도 글](/posts/smart-guide-snap-engine/)에 썼다.

2월 23일 커밋에는 드롭 위치 계산이 어긋난 문제를 적었다. 자식이 렌더되는 위치를 위젯이 정하게 했더니, 드롭하는 순간 가장 가까운 `position` 부모가 누구인지 알 수 없었다. 좌표 기준 문제는 이후 슬롯 설계에서 다시 나온다. 시리즈 5편에서 자세히 쓴다.

## 옛 빌더를 지웠다

새 코어가 자리를 잡은 뒤에도 첫 빌더는 석 달 가까이 코드에 남아 있었다. 뷰어가 그쪽 타입을 쓰고 있었기 때문이다. 화면 메타데이터 타입, 그리드 컬럼 선택용 옵션 아이템, 전역 다이얼로그 store가 옛 빌더 폴더에 있었다.

2026년 5월 8일, 이 의존을 하나씩 새 위치로 옮기고 폴더를 통째로 지웠다. 폴더 크기는 440KB였다. 같은 커밋에 Monaco 편집기 통합도 들어가서 108개 파일, 10,181줄이 삭제됐다. 옛 빌더에서 쓸 만했던 옵션 편집 팝업과 드래그 가능한 모달은 공용 위젯 컴포넌트로 빼서 살렸다.

> [!TIP]
> 새 구현을 만들어 놓고 옛 구현을 늦게 지울수록 옛 코드에 기대는 곳이 늘어난다. 지우기 전에 옛 폴더를 import하는 곳 목록부터 뽑아 두면 작업 범위가 정해진다.

## 재설계 문서와 적대적 검토

6월에는 멀티 패널 버그, 1,100줄로 불어난 캔버스 컴포넌트, 액션마다 복사된 동기화 코드가 쌓여 있었다. 전면 재작성을 할지 판단하려고 재설계 문서 묶음을 만들었다. 문서는 AI 코딩 에이전트 여러 개에게 나눠 쓰게 했다.

### 요구사항부터 코드에서 뽑았다

먼저 기능 목록과 불변식을 코드에서 추출했다. 불변식은 B1부터 B10까지 10개다. 그중 동시에 성립해야 하는 조건 셋이 설계를 가장 크게 묶었다.

- schema는 JSON으로 직렬화할 수 있어야 한다. 함수가 들어갈 수 없다.
- 위젯 메서드는 직렬화할 수 없다. schema 밖에 있어야 한다.
- 위치와 크기는 60fps로 바뀌는 동안 React 리렌더 없이 DOM에 반영돼야 한다.

세 조건을 한꺼번에 만족하는 store는 하나로 만들 수 없다. 그래서 저장 모델과 런타임 표현을 나누는 구조를 정식 설계로 받아들였다.

### 백지 검증과 적대적 검토

그다음 검토를 두 갈래로 따로 돌렸다. 하나는 백지 검증이다. 현재 코드를 보지 않고 요구사항만으로 처음부터 설계를 도출한 뒤 현행과 비교했다. 재작성을 정당화할 만큼 잘못 물려받은 결정은 하나도 나오지 않았다.

다른 하나는 문서 전체를 반박하는 역할을 맡긴 적대적 검토다. 문서의 주장을 실제 코드와 업계 1차 출처에 대조하게 했다. blocker 1건과 major 8건이 나왔다. blocker는 문서끼리의 모순이었다. 상위 문서는 "편집기용 미러 store 제거"를 기각했는데, 하위 문서 셋이 여전히 그 방향을 권장하고 있었다. 구현하는 사람이 하위 문서만 읽으면 기각된 설계를 만들게 된다.

업계 비교에서 빠진 내용도 잡혔다. puck은 0.19에서 슬롯 데이터를 전역 객체에서 부모 속성 안의 배열로 옮겼다. 그때 puck 팀은 삽입 82%, 재정렬 79%, 삭제 63% 성능 향상을 발표했다. 우리 문서는 이 전환을 언급하면서도 성능 수치는 빼고 "우리 모델과 맞지 않는다"는 말로만 넘어갔다.

검토 뒤에는 "결정"으로 적혀 있던 항목 셋을 PoC 게이트로 내렸다. 기존 화면 파일 전체로 변환 왕복과 생성 TSX가 그대로인지 확인하는 골든 회귀 스위트도 필수 조건에 넣었다. 전면 재작성은 하지 않기로 했다. 검증된 코어는 그대로 두고 세 곳만 정리한다.

> [!WARNING]
> 에이전트가 쓴 설계 문서는 그럴듯하고 길다. 같은 에이전트에게 반박 역할을 따로 맡겼더니 문서 간 모순과 제안을 결정처럼 써 놓은 부분이 금방 나왔다. 쓰는 단계와 의심하는 단계를 나눠 돌리는 편이 낫다.

## 라이브러리를 쓸지 직접 만들지

세 번 만들고 나서 보니 판단 기준은 단순했다. 요구사항이 라이브러리의 데이터 모델과 렌더 경로 바깥에 있으면 라이브러리는 출발점 이상이 되기 어렵다. 우리 빌더는 저장 모델, 런타임 메서드, 60fps 드래그를 직접 제어해야 했고, 모두 라이브러리 깊숙한 곳에 있는 부분이었다.

직접 만들 때 놓친 것도 있다. 첫 자체 빌더는 화면을 먼저 만들고 모델을 나중에 고쳤다. 캐시도 좌표계도 그렇게 고쳤다. 코어와 불변식을 먼저 정한 것은 세 번째 빌더에 와서였다.

## 정리

- 오픈소스 빌더를 열흘 남짓 붙여 보고 자체 구현으로 넘어갔다. 메서드, 60fps 드래그, 좌표 배치는 모두 라이브러리 안쪽을 고쳐야 하는 요구였다.
- 첫 자체 빌더는 화면부터 만들었다. WeakRef 모듈 캐시는 immer 상태와 맞지 않아 하루 만에 store 안으로 옮겼다.
- absolute 좌표 실험 뒤 세 번째 빌더는 정규화 모델과 patch 기반 undo부터 시작했다.
- 옛 빌더는 석 달 공존한 뒤 의존을 옮기고 한 번에 지웠다.
- 재설계는 요구사항 추출, 백지 검증, 적대적 검토 순서로 진행했고, 재작성 대신 세 곳을 정리하기로 했다.

다음 글부터는 코어 안쪽을 다룬다. 위젯 정의 방식과 위젯마다 둔 작은 store, 렌더 성능 순서로 쓴다.
